# GPU KMD Weekly #13

**日期：2026-11-07**  
**定位：Memory / UVM Owner 技术周报**

本期时间窗口严格截止 **2026-11-07**。后续 revision 可以作为“后续进展”索引，但不用于改变本期的历史判断。

# 本期重点

本周最值得关注的是两个 upstream 变化。

## 1. AMDGPU：TLB invalidation completion 正式进入 BO lifetime

AMDGPU user queue 场景暴露了一个典型的 GPU Memory correctness 问题：

```text
PTE 已经删除
      ≠
GPU 已经无法使用旧 translation
```

如果 BO 在此前的 TLB invalidation 真正完成之前就被释放，仍在运行的 user queue 可能通过 stale TLB entry 访问已经被释放甚至重新分配的 physical backing。

v2 修复把 `vm->last_tlb_inv` fence 挂到 BO reservation 上，使 BO lifetime 显式依赖最后一次相关 TLB invalidation completion。

[AMDGPU v2 — wait for TLB flush before freeing BO](https://mail-archive.com/amd-gfx%40lists.freedesktop.org/msg155047.html)

---

## 2. DMA-BUF：从固定 `sg_table` 向 Mapping Type negotiation 演进

DMA-BUF Mapping Types v2/23 保留了 RFC 的 mapping-type framework，但把最终 mapping type 的选择延后到第一次 pin/map。

Exporter 和 importer 先协商双方支持的候选 representation，真正 map 时 exporter 再根据 buffer placement 和其它 attachments 选择最终类型。该选择保持到 exporter 主动 invalidation，避免 unmap/remap 导致 buffer 在不同 placement 之间 ping-pong。

[DMA-BUF Mapping Types v2/23 cover letter](https://lists.openwall.net/netdev/2026/11/05/140)

这代表 dma-buf 的抽象正在从：

```text
shared buffer
      ↓
sg_table
```

向：

```text
shared buffer
      +
mapping representation
```

演进。

## A1. L4 · Memory/UVM — TLB invalidation completion 与 BO lifetime

AMDGPU 修复 GEM object close 与此前 GPUVA unmap 之间的 lifetime race：此前的 TLB invalidation 可能仍在进行，而 BO 已经开始进入释放路径。

核心变化不是“多 flush 一次 TLB”，而是建立：

```text
translation-cache completion
            ↓
BO lifetime dependency
```

这直接关系到 GPUVM、UVM fault、migration、eviction、reset generation 等 Memory Owner 基础设计。

[核心 v2 patch](https://mail-archive.com/amd-gfx%40lists.freedesktop.org/msg155047.html)  
[Focus →]({{ '/kmd_owner_direction/memory/focus/2026-11-07-tlb-bo-lifetime/' | relative_url }})

## A2. L3 · DMA-BUF — Mapping Types v2/23

传统 DMA-BUF attachment map 操作只支持 `struct scatterlist`，但 `dma_addr_t` 是一个具有特定 DMA address semantics 的类型，无法自然表达 VFIO/IOMMUFD、PCIe P2P、XGMI、VRAM 等所有共享内存场景。

Mapping Types 开始让 importer/exporter 显式协商双方都能理解的 mapping representation。

[Mapping Types v2/23](https://lists.openwall.net/netdev/2026/11/05/140)  
[Introduce DMA-BUF mapping types — patch 02/23](https://lists.openwall.net/netdev/2026/11/05/152)

## A3. L3 · PCIe P2P — Topology reachable ≠ DMA addressable

AMDGPU 修复一个很典型的 P2P capability 判定问题：`pci_p2pdma_distance()` 可以证明 PCIe topology 可达，但 importer 的 DMA mask 未必能覆盖 exporter VRAM BAR。

Patch 因此在 `dma_buf_attach()` 阶段进一步检查：

```text
IOMMU DMA remapping
        OR
peer aperture <= importer DMA mask
```

否则关闭该 attachment 的 peer2peer path。

[AMDGPU P2P DMA addressability patch](https://lists.openwall.net/linux-kernel/2026/11/04/194)

# B. Deep Dive：Memory / UVM 与强相关主题

# B1. L4 — TLB invalidation completion 为什么属于 BO lifetime

[打开 B1 Focus 页面 →]({{ '/kmd_owner_direction/memory/focus/2026-11-07-tlb-bo-lifetime/' | relative_url }})

## 0. 问题背景

### 0.1 这是一个什么问题？

这次 upstream 讨论的核心不是普通意义上的：

> “AMDGPU 某处忘记 flush TLB。”

真正的问题是：

> **GPU page-table mapping 已经删除之后，对应的 BO / physical backing memory 到底什么时候才能安全释放和重新使用？**

这个问题发生在 AMDGPU user queue 场景。

简化关系：

```text
GPU VA
  │
  ▼
GPU PTE
  │
  ▼
Physical Page / BO
```

BO 被 unmap 时：

```text
remove PTE
    ↓
issue TLB invalidation
```

但是 TLB invalidation 是一个异步硬件操作。

因此可能存在：

```text
PTE 已经删除
      │
      ▼
TLB invalidate 已发出
      │
      │   invalidate 尚未完成
      ▼
BO close / free
      │
      ▼
physical backing 被重新利用
```

AMDGPU v2 commit message 明确描述了这个 race：如果 BO 在 GEM close 前已经发生 unmap，`clear_freed()` 此前已经执行并留下空的 `vm->freed`，那么 close path 中就没有一个有意义的 fence 可以保证之前的 TLB flush 完成。Memory 因而可能先于 TLB flush completion 被释放，而仍在运行的 user queue 可以继续持有 stale address translation。

[核心 v2 patch](https://mail-archive.com/amd-gfx%40lists.freedesktop.org/msg155047.html)

### 0.2 影响是什么？

最危险的情况不是单纯 page fault：

```text
GPU VA X
   │
   ▼
PA Y
   │
   ▼
BO A

unmap

GPU PT:
VA X → INVALID

GPU TLB:
VA X → PA Y

BO A free
PA Y → allocator

PA Y reused
PA Y → BO B

old user queue
VA X
  ↓
stale TLB
  ↓
PA Y
  ↓
BO B
```

这意味着旧 workload 可能通过 BO A 的旧 VA translation 访问已经属于 BO B 的 backing。

潜在后果包括：

- GPU fault；
- random workload failure；
- silent memory corruption；
- stale cross-object access；
- information disclosure；
- 如果对象跨 security domain，则可能演变成 isolation 问题。

因此这里首先要建立：

```text
Page-table lifetime
        !=
Translation-cache lifetime
        !=
Memory-object lifetime
```

### 0.3 当前 upstream 方案与进展

Weekly #13 截止 **2026-11-07**。

当前版本是：

`[PATCH v2] drm/amdgpu: wait for tlb flush before freeing BO`

方案：

```text
last relevant TLB invalidation
              │
              ▼
       vm->last_tlb_inv
              │
              ▼
          dma_fence
              │
              ▼
          BO dma_resv
              │
              ▼
        BO free / reuse
```

- [完整 patch discussion thread](https://lore-kernel.gnuweeb.org/amd-gfx/f99b863b-9ad1-4fba-b6e0-b838849d5b1b%40amd.com/T/)

## 1. PTE 删除为什么不代表 translation 消失？

```text
GPU VA
  │
  ▼
GPU Page Table
  │
  ▼
PA
```

GPU 访问过该地址后：

```text
GPU TLB

VA → PA
```

现在 KMD 写：

```text
PTE = INVALID
```

software state 已经改变。

但：

```text
GPU TLB
VA → PA
```

可能仍存在。

所以 `PTE update` 只能证明 authoritative page-table state changed，不能证明 hardware can no longer consume the old translation。

## 2. 一个 GPU unmap 至少包含多个阶段

```text
T0 PTE update visible
 ↓
T1 TLB invalidate submitted
 ↓
T2 TLB invalidation completed
 ↓
T3 old translated accesses drained
 ↓
T4 BO / page reusable
```

这里自研 GPU 必须明确一个 HW/KMD contract：

> **TLB invalidation completion 是否同时意味着 invalidate 前已经获得 translation 的 memory requests 全部 drain？**

不能自动假设成立。

## 3. AMDGPU 的关键代码修改

修改位置：

```text
drivers/gpu/drm/amd/amdgpu/amdgpu_gem.c
└── amdgpu_gem_object_close()
```

v2 核心变化：

```c
if (r || !fence)
        goto out_tlb;

amdgpu_bo_fence(bo, fence, true);
dma_fence_put(fence);

out_tlb:
        amdgpu_bo_fence(bo, vm->last_tlb_inv, true);
```

重点不是增加了一行 `amdgpu_bo_fence()`，而是：

```text
vm->last_tlb_inv
       ↓
BO reservation
```

建立了 lifetime dependency。

## 4. 为什么 `clear_freed()` 返回的 fence 不够？

第一次 unmap：

```text
GPUVA unmap
    ↓
vm->freed
    ↓
amdgpu_vm_clear_freed()
    ↓
PT update + TLB invalidate
```

后来 GEM close：

```text
amdgpu_gem_object_close()
        ↓
amdgpu_vm_clear_freed()
```

但：

```text
vm->freed == empty
```

所以 close 这一次获得的 fence 不能保证代表 earlier relevant TLB invalidation。

## 5. `last_update` 与 `last_tlb_inv`

```text
             amdgpu_vm
                │
       ┌────────┴────────┐
       │                 │
  last_update       last_tlb_inv
       │                 │
       ▼                 ▼
 PT/VM update       translation-cache
 dependency           completion
```

架构原则：

> **两个异步动作即使通常连续发生，只要 completion semantics 和 consumer 不同，就应该拥有独立的 synchronization state。**

## 6. Translation lifetime 怎样进入 BO lifetime？

```text
amdgpu_vm
    │
last_tlb_inv
    │
 dma_fence
    │
    ▼
BO dma_resv
    │
    ▼
BO release
```

关键调用：

```c
amdgpu_bo_fence(bo, vm->last_tlb_inv, true);
```

它代表 Translation-cache lifetime → Memory-object lifetime。

## 7. 映射到自研 KMD

一个单纯：

```c
gpu_vm_tlb_flush(vm);
```

是不够的。

还必须能回答：

```text
flush 属于哪个 VM update？
影响哪个 VA range？
属于哪个 generation？
completion 是什么？
哪些 BO/page 依赖它？
reset 后旧 completion 是否仍有效？
physical page 什么时候可重新使用？
```

概念模型：

```text
gpu_vm
 ├── pte_generation
 ├── tlb_submit_seq
 ├── tlb_complete_seq
 └── last_tlb_fence

gpu_bo
 ├── mapping references
 ├── residency state
 ├── sync dependencies
 └── release eligibility
```

## 8. 到 UVM / recoverable fault 后问题会继续放大

```text
GPU fault
    ↓
fault worker
    ↓
HMM resolve
    ↓
migration
    ↓
GPU PTE publish
    ↓
TLB operation
    ↓
replay
```

CPU 同时可能 munmap / mprotect / COW / process exit；GPU/KMD 同时可能 context destroy / VM destroy / GPU reset / FW restart。

因此 UVM 需要的不仅是 TLB fence，还包括类似：

```text
mmu_notifier sequence
VM generation
context generation
recovery generation
TLB generation
```

## 9. 建议长期保存的 Memory invariant

```text
A physical page / BO may be reused

IFF

no valid GPU mapping references it

AND

all relevant translation-cache
invalidations completed

AND

old GPU/DMA accesses can no longer
reach the backing

AND

no stale fault / migration / replay
operation can republish the old mapping
```

## 10. Race / Lifetime Matrix

| Path A | Path B | 风险 | Lifetime / Sync |
|---|---|---|---|
| GPUVA unmap | running queue | stale translation | TLB completion |
| unmap | BO free | early reuse | BO reservation |
| BO free | new BO allocation | old VA accesses new BO | allocator + TLB |
| migration | invalidate | stale residency | migration + TLB |
| HMM fault | `munmap()` | stale PTE publish | mmu_notifier |
| replay | context destroy | stale execution | context generation |
| invalidate | GPU reset | stale completion | recovery generation |
| BO teardown | DMA engine | DMA after free | DMA completion |

## 11. 验证

主动放大 race：

```text
GPU:
loop access VA X

CPU/KMD:
unmap X
   ↓
delay TLB completion
   ↓
free BO A
   ↓
allocate BO B
```

重点检查 BO A 是否能在 TLB completion 前进入 allocator、old workload 是否能访问 BO B，以及 reset / stale fault worker 路径。

## 12. Observability

至少记录：

```text
device
VM / PASID
VA/range
BO ID
PTE generation
TLB invalidate seq
TLB completion seq
context generation
recovery generation
```

## 13. B1 结论

```text
PTE invalidation
      ≠
TLB invalidation completion
      ≠
old access disappearance
      ≠
physical memory reusable
```

# B2. L3 — DMA-BUF Mapping Types：为什么 `sg_table` 开始不够了？

[打开 B2 Focus 页面 →]({{ '/kmd_owner_direction/memory/focus/2026-11-07-dmabuf-mapping-types/' | relative_url }})

## 0. 问题背景

Linux dma-buf 传统 attachment mapping 接口的核心 representation 是 `struct sg_table`。这非常适合经典 device → DMA API → system pages 模型。

但 v2 cover letter 指出，dma-buf 现在需要服务的 use cases 已经超出单一 scatterlist/DMA address 模型。VFIO/IOMMUFD、vGPU、PCIe P2P 和 XGMI 等场景需要不同的 representation。

[DMA-BUF Mapping Types v2/23](https://lists.openwall.net/netdev/2026/11/05/140)

### 当前 upstream 在做什么？

```text
Importer supported types
           │
Exporter supported types
           │
           ▼
    compatible type set
           │
      first pin/map
           ▼
    exporter selects
     actual mapping
```

相比 RFC，v2 的重点变化是：不在 attach 时过早固定最终 mapping type。

### Source / code 索引

- [v2 cover letter](https://lists.openwall.net/netdev/2026/11/05/140)
- [Mapping Types API patch](https://lists.openwall.net/netdev/2026/11/05/152)
- [dma-buf.c](https://github.com/torvalds/linux/blob/master/drivers/dma-buf/dma-buf.c)
- [dma-buf.h](https://github.com/torvalds/linux/blob/master/include/linux/dma-buf.h)

## 1. Legacy dma-buf 心智模型

```text
Userspace
   │
dma-buf fd
   │
struct dma_buf
   │
   ├── exporter
   └── importer
         │
      attachment
         │
   map_attachment
         │
      sg_table
         │
    importer DMA
```

## 2. `dma_addr_t` 不等于通用 PA

`sg_dma_address(sg)` 返回的 `dma_addr_t` 表示的是某个 device 可用于 DMA 的地址。

有 IOMMU 时：

```text
Device
  │
 IOVA
  │
IOMMU
  │
physical page
```

所以：

```text
dma_addr_t != universal physical address
```

## 3. 为什么现在 `sg_table` 越来越难覆盖全部场景？

一个 dma-buf backing 可能是 system RAM / VRAM / peer VRAM / device-private memory，而 consumer 可能需要 IOVA / PCIe peer aperture / GPU PA / IOMMUFD representation / XGMI address。

```text
Memory Object
      │
      ├── backing
      ├── placement
      └── address representations
```

## 4. Mapping Types 在改变 abstraction 的哪一层？

旧模型：

```text
dma_buf
   ↓
attachment
   ↓
map
   ↓
sg_table
```

新模型：

```text
dma_buf
   ↓
attachment
   ↓
mapping-type negotiation
   ↓
select representation
   ↓
type-specific map
```

真正变化是从 “give me a scatterlist” 变成 “which mapping representation can both sides understand?”

## 5. 为什么最终 type 延迟到第一次 pin/map？

因为 exporter 的 buffer placement 可能变化：

```text
VRAM
  ↓
eviction
  ↓
System RAM
```

attach 时过早决定 representation 未必适合最终 backing；每次 remap 都重新选择又可能导致 placement ping-pong。

## 6. 与 Memory/UVM 的关系

```text
Memory Object
        ≠
Address Representation
        ≠
Device Accessibility
```

一个 logical memory object 可以同时拥有多个不同 representation。

## 7. B2 结论

```text
shared-memory contract
 =
memory object
+
representation negotiation
+
consumer capability
```

# B3. L3 — PCIe P2P：Topology reachable ≠ DMA addressable

[打开 B3 Focus 页面 →]({{ '/kmd_owner_direction/memory/focus/2026-11-07-pcie-p2p-addressability/' | relative_url }})

## 0. 问题背景

`pci_p2pdma_distance() >= 0` 可以证明 PCIe topology 可达，但 importer 自己的 DMA address width 可能根本无法表示 exporter VRAM BAR aperture。

[AMDGPU addressability patch](https://lists.openwall.net/linux-kernel/2026/11/04/194)

### 当前 upstream 方案

```text
if IOMMU DMA remapping available
    potentially addressable
else
    peer aperture end
          <=
    importer DMA mask
```

### Source / code 索引

- [AMDGPU patch](https://lists.openwall.net/linux-kernel/2026/11/04/194)
- [PCI P2PDMA source](https://github.com/torvalds/linux/blob/master/drivers/pci/p2pdma.c)
- [DMA direct source](https://github.com/torvalds/linux/blob/master/kernel/dma/direct.c)

## 1. P2P capability 为什么不是一个 bool？

```text
P2P usable
 =
 topology reachable
 &&
 routing allowed
 &&
 ACS configuration compatible
 &&
 target aperture addressable
 &&
 DMA mask sufficient
 &&
 IOMMU mode compatible
 &&
 mapping representation compatible
```

## 2. DMA mask 的角色

如果 importer 支持 40-bit DMA，它最大能发出的 DMA address 大约是 `2^40 - 1`。如果 peer BAR 超过这个范围，PCIe switch 即使能 route transaction，DMA initiator 也发不出目标地址。

## 3. Topology 与 addressability 是两个不同维度

```text
Topology Layer:
route exists

Address Layer:
can initiator encode target address?
```

`pci_p2pdma_distance() >= 0` 最多回答 topology 是否适合，不能单独回答 DMA initiator 是否能发出目标地址。

## 4. IOMMU 为什么会改变结论？

无 IOMMU/direct mode：

```text
Importer
   │
DMA address
   │
PCIe peer BAR
```

有 DMA-remapping IOMMU：

```text
Importer
   │
IOVA
   │
IOMMU
   │
Peer resource
```

如果 IOMMU 可以合法建立 peer-resource mapping，device 可能只需要发出自己的 IOVA。

## 5. 为什么 capability 很可能是方向性的？

```text
A → B : YES
B → A : NO
```

因此 `bool p2p_supported(A, B)` 往往过于简单，设计上更适合保存 source/destination/direction/address type/DMA width/IOMMU/topology/rejection reason。

## 6. 把 B2 和 B3 合起来

```text
Memory Object
     │
Mapping Type
     │
DMA / IOMMU Address
     │
PCIe Routing
     │
Hardware Addressability
```

## 7. B3 结论

```text
Topology reachability
       !=
DMA addressability
       !=
Usable P2P mapping
```

# 总结回顾

## 本周最值得记住什么？

三个 Deep Dive 看似分别属于 GPUVM、DMA-BUF、PCIe P2P，但实际上可以串成同一条 Memory 主线：

```text
               Memory Object
                    │
       ┌────────────┼────────────┐
       │            │            │
       ▼            ▼            ▼
   Lifetime      Mapping      Hardware
                Representation Addressability
```

### B1 回答的是

> 这个 physical backing **什么时候仍然属于旧 mapping 的可达范围？**

### B2 回答的是

> 这个 memory object **应该以什么 representation 交给另一个 subsystem/device？**

### B3 回答的是

> 即使 representation 正确，目标 hardware **是否真的能访问它？**

## 本周补出的关键 Memory Owner 心智模型

以后面对一个 GPU memory sharing / migration / UVM / P2P 问题，可以连续问：

```text
1. Memory Object 当前 backing 是什么？
2. 当前 mapping / residency 是什么？
3. Consumer 使用哪种 address representation？
4. Consumer hardware 真能访问这个地址吗？
5. Mapping revoke 后，什么时候 backing 才安全复用？
```

这五个问题可以把 GPUVM、HMM/UVM、DMA-BUF、IOMMU、PCIe P2P、migration、eviction 逐渐收敛到同一套 Memory architecture 语言中。
