## A. 本期最值得推进的 Feature

7 个稳定 Owner 不变，本期继续把它们落到可长期复用的 KMD 基础设施：

1. **Memory / P0**：Recoverable Fault + HMM + Migration + Replay，并保留 migration granularity 抽象。
2. **Firmware / P0**：Versioned Async Protocol + Capability Negotiation + restart/state reconciliation。
3. **Reliability / P0/P1**：Hang Snapshot + devcoredump + FW Log + Reset Reason。
4. **Multi-GPU / P1**：Stable Identity + Topology + P2P Capability Model。
5. **Observability / P1**：Stable GPU Event/Object Identity + eBPF trace，PMU 后续接入同一 timeline。
6. **Virtualization / 条件 P1**：仅在 ASIC 真正具备 SR-IOV/resource partition 能力时推进。
7. **Power / P1/P2**：Reusable telemetry → DVFS/runtime PM。

## B. Memory

当前主线仍然是：

```text
GPU fault
→ PASID / VM / context
→ process mm / CPU VA
→ HMM / CPU PTE state
→ residency / migration
→ GPU PTE
→ TLB invalidate
→ replay
```

本期进一步关注 Linux GPU SVM / drm_pagemap 的 N:1 per-device state。一个 logical CPU VA/range 可以共享 notifier/range identity，但每个 DRM device 仍维护独立的 DMA mapping / residency / GPU PTE state。

因此未来 multi-GPU UVM 的数据模型不应把以下状态合成一个对象：

```text
CPU range identity
≠ device residency
≠ DMA mapping
≠ GPU PTE ownership
```

相关参考：
https://docs.kernel.org/next/gpu/rfc/gpusvm.html
https://docs.kernel.org/mm/hmm.html

## C. Virtualization / Security

Xe 的 SR-IOV lifecycle/configuration 继续说明：GPU virtualization 的重点不是 generic PCI SR-IOV API，而是 pre-probe mode、resource provisioning、VF reset/isolation、PF↔VF control 和 GPU-specific resource ownership。

Nova lower layer 同时面向 DRM 与可能的 VFIO/vGPU upper client，也继续验证“共享 control/resource service”比复制一套 vGPU hardware path 更合理。

参考：
https://docs.kernel.org/gpu/nova/index.html

## D. Power / Performance

本期没有改变路线的新机制。仍保持：

```text
measurement / lifetime correctness
→ reusable utilization telemetry
→ DVFS
→ runtime PM
→ complex policy later
```

Power telemetry 应与 Profiling 共享基础计量层，而不是成为某个 governor 私有接口。

参考 Xe PM：
https://docs.kernel.org/gpu/xe/xe_pm.html

## E. Reliability / Recovery / RAS

两个最重要的架构不变量保持不变：

- destructive recovery 前 snapshot；
- FW logs / reset reason 与 GPU state 一起进入 crash object。

第一阶段先把 hang 时的 register/ring/VM/context/FW evidence 冻结下来，再逐步推进 job/queue/context/engine/GPU 分级恢复。

参考：
https://docs.kernel.org/gpu/xe/xe_devcoredump.html
https://docs.kernel.org/gpu/nova/core/todo.html

## F. Multi-GPU / P2P / Fabric

继续坚持 topology-first：stable identity → topology → visibility/affinity → P2P capability → peer transport → shared VM。

GPU SVM N:1 per-device state 是未来 shared VA 的重要数据模型信号；`fabric_ext` 则继续作为 movement / ordering / ownership / observability 的长期研究信号。

参考：
https://docs.kernel.org/next/gpu/rfc/gpusvm.html
https://arxiv.org/abs/2607.26335

## G. Observability / Profiling

### 本期详细 Feature：Stable GPU Event/Object Identity

如果不先统一 identity，trace、PMU、RAS、Memory fault debug 很容易各自建立不兼容的 ID 和 timestamp。

建议第一阶段稳定定义：

```text
device
client / PID / PASID
VM
context
queue
job
fault
migration
FW message
reset generation
```

3–6 个月：

- 为关键 lifetime edge 建立稳定 tracepoint；
- tracepoint 携带统一对象 ID；
- 做一个用户态 correlation 工具；
- eBPF/fentry/fexit 用于动态补充观察，而不是替代稳定事件模型。

1–2 年：

- 加入 FW timestamp domain；
- 加入 GPU PMU samples；
- 做 per-context attribution；
- crash snapshot 复用同一套 object IDs；
- 最后扩展到 multi-GPU/fabric timeline。

ProfInfer / gpu_ext 是重要参考：
https://arxiv.org/abs/2601.20755
https://arxiv.org/abs/2512.12615

## H. Firmware / Control Plane

Nova guidelines 明确把 **firmware-version-independent API** 作为 lower-layer invariant：上层 DRM/VFIO client 不应该看到某个 GSP firmware version 特有的结构或语义。

因此 KMD↔FW control plane 应集中负责：

- protocol version；
- capability negotiation；
- version translation；
- sequence / async completion；
- timeout/error；
- restart generation；
- re-handshake；
- state reconciliation；
- FW health/log service。

参考：
https://docs.kernel.org/next/gpu/nova/core/guidelines.html
https://docs.kernel.org/gpu/nova/core/todo.html
