## A. 本期最值得推进的方向

7 个稳定 Owner 不变。本期重点不是再增加方向，而是把现有方向进一步变成可实现、可验证、可长期扩展的 KMD feature。

当前优先级：

1. **Memory / P0**：Recoverable GPU Fault + HMM + Migration + Replay；第一版就保留 migration granularity 与 multi-device metadata。
2. **Firmware / P0**：Versioned Async KMD↔FW Control Protocol + Capability Negotiation + restart generation/state reconciliation。
3. **Reliability / P0/P1**：Frozen Hang Snapshot + devcoredump + FW logs + persistent reset reason。
4. **Observability / P1**：Stable GPU Event/Object Identity + eBPF tracing，PMU 后续接入同一 timeline。
5. **Multi-GPU / P1**：Stable Identity + Topology + P2P Capability Matrix，shared VM 放在后面。
6. **条件方向**：ASIC 真正支持 SR-IOV 时做 PF/VF provisioning；否则优先 reusable utilization telemetry → DVFS/runtime PM。

## B. Memory / UVM

### 本期最重要的新收敛：Recoverable GPU Fault Service Contract

第一版 recoverable fault 不能只做到“收到 fault → 补一条 PTE → replay”，而应从一开始把 lifetime、MMU invalidation、teardown 与 reset generation 明确写进 contract。

推荐状态流：

```text
GPU access
  ↓
fault packet
  ↓
resolve device / PASID / VM / context
  ↓
validate VM/context/reset generation
  ↓
find process mm / CPU VA
  ↓
HMM / CPU PTE snapshot under notifier sequencing
  ↓
classify invalid / resident / map / migrate
  ↓
DMA + residency resolution
  ↓
GPU PTE update
  ↓
TLB invalidate
  ↓
re-check generation / teardown
  ↓
replay or terminate
```

第一版就应覆盖：

- `munmap()`；
- `mprotect()`；
- COW/fork；
- process exit；
- VM/context teardown；
- migration completion race；
- GPU/FW reset during fault；
- duplicate/concurrent fault。

建议区分：`vm_generation`、`context_generation`、`reset_generation`、per-range notifier sequence 与 migration state，不要试图用一个 generation counter 覆盖所有 ownership domain。

参考：
https://docs.kernel.org/mm/hmm.html
https://docs.kernel.org/next/gpu/rfc/gpusvm.html

### N:1 per-device state

一个 logical CPU range 可以共享 range/notifier identity，但不同 GPU 仍拥有独立 DMA mapping、residency 与 GPU PTE state。未来 multi-GPU shared VA 的数据模型应从现在就保留这种分层。

## C. Virtualization / Security

本期仍然坚持 capability-first。只有 ASIC 真正提供 SR-IOV、resource partition、VF reset/isolation 等硬件能力，才把 PF/VF provisioning 作为独立 feature。

长期新增一个值得观察的信号：CXL Type-2 accelerator passthrough 说明未来 VFIO 可能不仅是 BAR/IRQ/IOMMU mapping，还会涉及 HDM decoder、memory region 和 component-register virtualization。

参考：
https://lwn.net/Articles/1079613/

## D. Power / Performance

本期没有改变路线的新机制。仍坚持 reusable telemetry first：

```text
busy/idle
→ engine utilization
→ frequency residency
→ memory-bandwidth telemetry
→ DVFS
→ runtime PM
→ thermal / power cap
```

telemetry 同时服务 PM 与 Profiling；runtime PM 先解决 active-reference ownership、resource ordering 和 resume correctness，再谈复杂 governor。

参考：
https://docs.kernel.org/gpu/xe/xe_pm.html

## E. Reliability / RAS

### Structured post-mortem artifact

跨厂商 crash tooling 都在从“寄存器 dump”演进到结构化、可离线消费的 crash artifact。

建议自研 KMD 的 crash object 逐步包含 versioned sections：

- reset generation；
- KMD/FW version；
- FW generation / logs；
- queue/context/job identity；
- VM/page-fault summary；
- ring/doorbell state；
- interrupt state；
- relevant registers；
- execution markers（有条件时）。

**snapshot-before-reset 仍是硬约束。**

参考：
https://docs.kernel.org/gpu/xe/xe_devcoredump.html
https://gpuopen.com/learn/radeon-developer-tool-suite-amd-rdna4/

## F. Multi-GPU / P2P / Fabric

继续 topology-first：

```text
identity
→ topology
→ visibility / affinity
→ P2P capability
→ peer mapping
→ P2P DMA
→ shared VM
```

`fabric_ext` 是长期值得关注的研究信号：未来 Fabric interface 可能需要表达 movement、ordering、ownership、link health 等语义，而不仅仅是 peer-copy yes/no。

参考：
https://arxiv.org/abs/2607.26335

## G. Observability / Profiling

本期最重要的信号是：stable object ID + timestamp 应当被视为长期基础设施，而不是一次性 debug script。

推荐统一对象模型：

```text
device
→ client / PID / PASID
→ VM
→ context
→ queue
→ job
  ↘ fault / migration / FW seq / reset generation
```

software trace、FW event、PMU sample 和 crash snapshot 尽量复用这套 identity。

SysOM-AI 展示了 continuous cross-layer diagnosis 在大规模 GPU 生产环境中低开销运行的可能性；Radeon GPU Profiler 则体现了 timeline 与 hardware counter 的统一消费方式。

参考：
https://arxiv.org/abs/2603.29235
https://gpuopen.com/rgp/

## H. Firmware / Control Plane

继续把 firmware-version independence 当作硬约束。上层 DRM/VFIO/Power/RAS service 只看稳定命令、capability 和 state model，FW-version-specific translation 留在 lower control layer。

Nova 是当前最重要的公开参考：
https://docs.kernel.org/next/gpu/nova/core/guidelines.html

早期 NVK→Nova backend 也说明 userspace 与新 KMD 会并行演进，因此 lower ABI/capability contract 越稳定越重要。
