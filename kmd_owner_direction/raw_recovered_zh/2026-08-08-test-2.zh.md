## 一、本期核心结论

本期保持 **7 个一级 Owner + 1 个公共 Future Topic** 不变，但进一步把各方向从“概念分类”落到当前可做的独立 KMD feature。

当前优先级仍然是：

1. **Memory / P0**：Recoverable GPU Page Fault + HMM/SVM + Migration + Replay。
2. **Firmware / P0**：Versioned Async KMD↔FW Protocol + Capability Negotiation + restart/state reconciliation。
3. **Reliability / P0/P1**：Hang Snapshot + devcoredump + FW logs + reset reason。
4. **Multi-GPU / P1**：Stable Identity + Topology + Visibility/Affinity + P2P Capability Matrix。
5. **Observability / P1**：eBPF KMD Trace + GPU Object Correlation，之后再接入 PMU。
6. **Virtualization / 条件 P1**：只有 ASIC 真正支持 SR-IOV/resource partition 时才推进 PF/VF provisioning。
7. **Power / P1/P2**：先做 reusable utilization telemetry，再进入 DVFS/runtime PM。

## 二、Memory：Migration Granularity 被提升为第二阶段架构项

本期最重要的新收敛，是明确：**migration granularity 不是实现细节，而是 Memory Owner 第二阶段必须独立设计的架构概念。**

需要从一开始就区分：

```text
CPU base page
    ≠ fault range
    ≠ migration unit
    ≠ DMA mapping unit
    ≠ GPU PTE unit
    ≠ TLB invalidation unit
```

第一版可以先保证 4K correctness，但 ownership/lifetime/API 不应把 4K 写死。后续自然演进到 batched 4K、64K、2M、compound device pages 和 higher-order DMA mapping。

相关方向可参考 Linux DRM GPU SVM / drm_pagemap：
https://www.kernel.org/doc/html/latest/gpu/rfc/gpusvm.html

## 三、Firmware / Control Plane

继续把 firmware version isolation 提升为核心约束。不要在各 feature 内散落：

```text
if (fw_version >= X) ...
```

而应集中形成：

- protocol version；
- capability bitmap；
- version-specific translation；
- sequence ID / async completion；
- timeout / error / unsupported；
- restart generation；
- re-handshake；
- state reconciliation。

Nova 的 lower-layer / firmware-centric 架构仍然是重要参考：
https://docs.kernel.org/gpu/nova/index.html
https://docs.kernel.org/gpu/nova/core/todo.html

## 四、Reliability / RAS

本期进一步确认两个硬约束：

1. **snapshot-before-reset**：destructive recovery 前必须冻结唯一有效的 hang state；
2. **FW log retention**：firmware log、甚至 probe/early boot failure，也应进入统一 crash artifact。

推荐恢复梯度仍是：

```text
job abort
→ queue kill
→ context kill
→ engine reset
→ partial reset
→ full GPU reset
```

参考 Xe devcoredump：
https://docs.kernel.org/gpu/xe/xe_devcoredump.html

## 五、Multi-GPU / P2P / Fabric

短期仍然坚持 topology-first：

```text
stable GPU identity
→ visibility / affinity
→ PCIe / NUMA topology
→ P2P capability
→ peer mapping / P2P DMA
→ shared VM
```

Memory Owner 负责 page residency/migration/shared-VM policy；Multi-GPU Owner 负责 identity/topology/connectivity/peer mechanism。

长期关注 `fabric_ext` 对 GPU/DPU/CXL movement、ordering、ownership 和 observability 的抽象，但目前只作为研究信号：
https://arxiv.org/abs/2607.26335

## 六、Observability / Profiling

本期明确软件 trace 与硬件 PMU 最终应进入同一条 timeline：

```text
UMD event
→ KMD trace
→ FW event
→ GPU PMU sample
→ unified object/timestamp correlation
```

近期先完成稳定 tracepoint 与 PID/PASID/VM/context/queue/job 对象关联；硬件 counter 成熟后再加入 PMU discovery、sampling、multiplexing 和 per-context attribution。

ProfInfer 是重要参考：
https://arxiv.org/abs/2601.20755

## 七、Virtualization / Security

不要把 `pci_enable_sriov()` 当成 GPU virtualization feature 本身。先做 Hardware Virtualization Capability Assessment：

- ASIC 是否真实支持 SR-IOV；
- VF BAR / interrupt model；
- VMID / queue / doorbell / memory partition；
- PF↔VF control path；
- VF FLR/reset；
- IOMMU isolation。

如果硬件条件不存在，则这一阶段不强行建立独立 SR-IOV 项目。

## 八、Power / Performance

继续坚持 measurement-first：

```text
busy/idle
→ per-engine utilization
→ frequency residency
→ memory-bandwidth telemetry
→ basic DVFS
→ runtime PM
→ thermal / power cap
```

telemetry 应当同时服务 PM policy 与 Profiling，而不是只属于某个 governor。

## 十、本期详细 Feature：Migration Granularity Architecture

推荐把 migration pipeline 显式建模为：

```text
fault range
→ residency decision
→ migration unit selection
→ DMA mapping unit
→ GPU PTE update unit
→ TLB invalidation unit
→ replay
```

3–6 个月内至少完成：记录所有 page-size assumption、引入 migration-unit descriptor、测量 4K migration 的 MM/DMA/copy/PTE/TLB 成本，并在硬件/IOMMU 允许时验证 batched/higher-order mapping。

本期不增加第八个 Owner；新的信号仍然加强 Memory、Firmware、RAS、Multi-GPU、Observability 等已有方向。
