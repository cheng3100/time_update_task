## A. 本期最值得新增 / 增强的 Feature

本期七个一级 Owner taxonomy 保持不变，最值得加强的是三个跨 Owner 的长期 contract：

1. **RAS — Reset Gate + Reset Generation Contract**：把 reset admission、reset generation、normal-operation gate 从某个 recovery path 的局部逻辑提升为可复用的 RAS 基础设施。Tyr GPU reset v4 是本期最值得参考的 upstream case。
2. **Virtualization — PF↔VF Admin Channel / Control Plane**：如果 ASIC 真正支持 SR-IOV，不再把重点放在 `pci_enable_sriov()`，而是明确 PF↔VF 的版本化 admin channel、request/completion、interrupt、teardown/reset ordering 与资源 ownership。Cisco enic SR-IOV V2 是很好的跨子系统实现参考。
3. **Firmware — Stable Capability / Property Service**：nova-core 当前 parameter/property export 进一步证明，底层 control plane 应提供 firmware/HW-version-independent capability/property object，供 DRM、VFIO/vGPU 等上层 client 消费。
4. **Memory — Recoverable Fault + HMM + Migration + Replay**：主线不变，继续强化 fault/replay race correctness、TLB invalidation completion/ordering 和 measurement contract。
5. **Observability — Hardware Trace / perf AUX Future Integration**：software counters + stable object/event IDs + eBPF 仍是近期主线；perf AUX kernel-consumer 工作是未来把硬件 trace stream 接入统一 observability infrastructure 的重要信号。

Power 与 Multi-GPU 本期没有足够高价值的方向级新变化，不为了“每期必须有新闻”而制造变化。

## B. 七个 Owner + 子方向雷达

### 1. GPU Memory / Virtual Memory / Unified Memory
稳定子方向继续包括：GPUVM/page table/VMID/PASID/TLB、recoverable fault/replay、mmu_notifier/HMM/SVM/device-private、CPU↔GPU migration、oversubscription/eviction/reclaim、NUMA/large/compound pages、IOMMU/ATS/PRI/PASID/SVA、dma-buf/P2P memory、multi-GPU UVM。

当前优先级仍然是：

- recoverable fault / replay correctness：P0；
- HMM + migration + GPU PTE + TLB ordering：P0；
- measurement / race matrix：P0；
- migration granularity：P1；
- oversubscription / eviction：P1/P2；
- multi-GPU UVM：后续。

### 2. GPU Virtualization / Security
稳定子方向：VFIO、IOMMU isolation、SR-IOV PF/VF、resource provisioning、VMID/queue/doorbell/interrupt/memory partition、PF↔VF ABI、VF FLR/reset、vGPU/live migration、secure boot/measurement/scrub/attestation。

本期把 **PF↔VF admin channel** 明确提升为 ASIC 支持 SR-IOV 后必须设计的独立 control-plane feature。

### 3. GPU Power / Performance
稳定子方向：busy/idle/utilization、runtime PM/system suspend、clock/power gating、DVFS/OPP、thermal/power cap、frequency residency/memory bandwidth、FW PM protocol、ASPM。

本期无高价值方向级新变化，继续坚持 measurement/lifetime correctness → reusable telemetry → DVFS/runtime PM。

### 4. GPU Reliability / Recovery / RAS
稳定子方向：heartbeat/watchdog、snapshot/devcoredump/reset reason、job/queue/context/engine recovery、partial/full reset、post-reset restore/replay、FW crash recovery、ECC CE/UE、bad-page retirement、AER、fault injection。

本期最重要变化：在 snapshot-before-reset 之后，增加 **reset gate + reset generation** 作为通用基础设施。

### 5. Multi-GPU / P2P / Fabric
稳定子方向：enumeration/stable identity、topology、visibility/affinity、P2P capability、peer BAR/PTE、P2P DMA、cross-GPU dma-buf、shared VM、multi-GPU UVM、fabric health/reset。

本期无生产级新方向，继续 topology-first：identity → topology → P2P matrix → peer mapping → P2P DMA → shared VM。

### 6. GPU Observability / Profiling / Programmable Driver Infrastructure
稳定子方向：software counters、stable tracepoint/event model、BTF/CO-RE/eBPF、PID/PASID/VM/context/queue/job correlation、GPUVM/fault/migration trace、UMD/KMD/FW/GPU timeline、PMU counters/sampling/multiplexing、perf_event、dynamic diagnostics、future programmable hooks。

本期新增长期信号：perf AUX kernel-consumer API 可能成为硬件 trace stream 接入统一 Linux observability stack 的重要接口方向。

### 7. GPU Firmware / Control Plane Architecture
稳定子方向：versioned FW ABI、command/event namespace、ring/mailbox/shared memory、sequence/async/timeout/error、capability negotiation、boot/restart/upgrade/rollback、resource ownership/state reconciliation、FW-centric init/PM/reset/HW scheduler、FW health/log/auth。

本期进一步明确：底层应该提供稳定的 **capability/property service**，屏蔽 firmware/HW-specific property 获取方式。

## C. 每个 Owner 当前切入点

- **Memory**：fault → PASID/VM/context → HMM/CPU PTE resolution → optional migration → GPU PTE publish → TLB invalidate → replay，同时保留 notifier/VM/context/reset generation correctness。
- **Virtualization**：ASIC capability gate；支持 SR-IOV 时做 provisioning/isolation + PF↔VF admin channel。
- **Power**：busy/idle + per-engine utilization → reusable telemetry → DVFS/runtime PM。
- **RAS**：hang detect → frozen snapshot → reset admission gate → reset generation → reset/restore/replay。
- **Multi-GPU**：stable identity → topology graph → visibility/affinity → P2P capability matrix。
- **Observability**：stable object/event IDs + software counters + tracepoint/eBPF；PMU/hardware trace 后续接入同一 timeline。
- **Firmware**：versioned async protocol + capability/property object + boot/reset generation + re-handshake/state reconciliation。

## D. Industry Updates

### Memory
本期没有足以改变 GPU SVM/HMM 总体路线的新机制，但 Linux 7.2 相关 AMDGPU 修复继续强化一个关键判断：**TLB invalidation completion/ordering 是 fault/migration correctness 的正式一部分，不是迁移流程末尾的“小动作”。**

对于自研 KMD，fault/replay pipeline 应显式记录：PTE publish、TLB invalidation submit/completion、generation re-check、replay ordering。

本期结论：Memory 路线不变，继续 measurement + race correctness。

### Virtualization / Security
Cisco enic SR-IOV V2 v13（2026-08-12）实现了直接 PF↔VF admin channel，并为 control path 使用独立 WQ/RQ/CQ、MSI-X 与 mailbox protocol。

它不是 GPU 实现模板，但非常适合作为 **PF/VF control-plane pattern** 学习：

- transport resource 如何 ownership；
- request/completion 如何版本化；
- interrupt / mailbox 如何配合；
- teardown / VF reset / PF reset 如何排序；
- stale completion 如何隔离。

对 GPU KMD 的意义：SR-IOV owner 的真正难点不是打开 VF，而是 GPU-specific resource provisioning + isolation + PF↔VF ABI/control path。

### Power / Performance
本期没有高价值 GPU-specific 方向级变化。

继续坚持：

```text
measurement / lifetime correctness
→ utilization telemetry
→ DVFS
→ runtime PM
→ complex governor later
```

### Reliability / Recovery / RAS
Tyr GPU reset v4（2026-08-13）使用 dedicated reset workqueue、显式 pending/in-progress state，并使用 SRCU gate 在 reset 周围阻止或允许正常 operation。

这给自研 KMD 一个很直接的 feature 结论：**reset gate 不应散落在 submission/ioctl/FW path 的多个 `if (resetting)` 中，而应成为统一 admission primitive。**

建议状态机：

```text
RUNNING
  ↓
QUIESCING
  ↓
SNAPSHOT_FROZEN
  ↓
RESETTING
  ↓
RESTORING
  ↓
RUNNING / FAILED
```

并给 async request/job/resource 携带 `reset_generation`，reset 后拒绝上一代 stale completion。

### Multi-GPU / P2P / Fabric
本期无新的 production-level 方向变化。

仍坚持：

```text
identity
→ topology
→ visibility / affinity
→ P2P capability
→ peer mapping
→ P2P DMA
→ shared VM
```

shared residency policy 继续属于 Memory Owner；Multi-GPU Owner 负责 topology/connectivity/peer mechanism。

### Observability / Profiling
Perf AUX kernel-consumer API RFC 与 DAMON / ARM SPE 的结合说明 Linux 正在探索让内核框架直接消费 hardware-generated trace stream。

对 GPU 的长期启发是：如果未来 GPU 提供硬件 trace/PMU stream，优先考虑与 perf-compatible event semantics / common timestamp / object IDs 对齐，而不是再造一个完全封闭的 vendor-only stream。

近期仍然是：

```text
software counters
+ stable object IDs
+ tracepoint/eBPF
→ PMU
→ hardware trace
→ unified timeline
```

### Firmware / Control Plane
Nova parameter-export v4（2026-08-11）从 nova-core 向 nova-drm 暴露基本 GPU properties，并进一步服务 GPU-info ioctl。

这说明 firmware-centric KMD 的 lower layer 不应该只提供“发送 FW command”的 transport，而应向上提供稳定的 property/capability object，例如：

- supported engines；
- memory topology/capacity；
- FW capability bitmap；
- reset/PM capability；
- scheduler / queue feature；
- security / virtualization capability。

Nova PRAMIN 工作同时说明 lower layer 应明确 typed MMIO/window ownership，而不是让多个 upper client 直接碰底层窗口。

## E. 本期长期 Learning Resources 新增 / 替换

本期明确新增一项长期 Implementation / Practice 资料：

### Virtualization / PF↔VF ABI & Reset — Cisco enic SR-IOV V2 admin channel

价值不在 NIC-specific queue 设计，而在通用 PF/VF control plane：transport、request/completion、interrupt、teardown/reset ordering 和 ownership。

它应和 GPU-specific Xe SR-IOV lifecycle、VFIO/IOMMU isolation 资料互补，而不是替代 GPU canonical reference。

## G. 本期重点 Feature 深挖 — Reset Gate + Generation Contract

### 目标
把 reset 从“异常路径里的大函数”变成有明确 admission、evidence freeze、generation 和 restore contract 的 KMD subsystem。

### 3–6 个月建议状态

```text
RUNNING
→ QUIESCING
→ SNAPSHOT_FROZEN
→ RESETTING
→ RESTORING
→ RUNNING / FAILED
```

### Admission API
至少以下入口都应经过统一 reset gate：

- submission / queue submit；
- ioctl that mutates GPU state；
- VM bind/unbind；
- FW control request；
- PM transition；
- selected debug/telemetry paths。

不同操作可以有不同 policy：block、fail-fast、allow-read-only 或 drain。

### Reset request coalescing
多个 fault/hang/heartbeat timeout 同时触发 reset 时，不应重复启动 reset。需要：

- pending reset reason set；
- reset owner/workqueue；
- coalescing；
- highest-severity reason；
- generation increment boundary。

### Generation
建议至少维护：

```text
reset_generation
```

并让以下对象在创建时记录 generation：

- async FW request；
- submitted job；
- queue/context restore work；
- fault/replay work；
- PM async work。

completion 返回后如果 generation 已变化，则不能继续作用于新一代 GPU state。

### Fault injection
第一阶段必须覆盖：

- reset 与 submit 并发；
- reset 与 remove/unbind 并发；
- reset 与 FW completion 并发；
- reset 与 VM/context destroy 并发；
- reset 中再次触发 reset；
- restore 失败；
- stale async completion after reset。

### 1–2 年
逐步进入：

- queue/context scoped recovery；
- engine scoped reset；
- replay eligibility contract；
- health/recovery hints；
- hierarchical generations；
- multi-GPU / fabric scoped recovery。

## H. VFIO / SR-IOV

仍然硬件能力 gate。若 ASIC 支持真实 SR-IOV，需要把以下能力一起评估：VF BAR、MSI-X、VMID、queue/doorbell/interrupt partition、memory ownership、PF↔VF admin channel、VF FLR、PF reset 对 VF 的影响、IOMMU isolation。

## I. Power

本期无方向变化。继续优先 measurement、reference lifetime、runtime suspend/resume correctness，再考虑 governor。

## J. RAS

本期新增的核心是 reset gate + generation。snapshot-before-reset 仍是硬约束：先冻结 evidence，再进入 destructive reset。

## K. Multi-GPU

仍然 topology-first，不提前进入 shared VM/fabric policy。

## L. Observability

software counters、tracepoint/eBPF、PMU 和 future hardware trace 需要共享 object identity 与 timestamp/correlation model。

## M. Firmware

构建一个稳定 capability/property object，位于 DRM/VFIO/Power/RAS 等 upper client 之下，屏蔽 firmware-version-specific property access。

## N. Future Topic

继续观察：Linux 7.2/7.3 DRM 演进、GPU SVM/drm_pagemap、Nova、perf AUX/hardware trace integration、VFIO + CXL Type-2、gpu_ext/fabric_ext。

## O. 8–10 人拆分

团队扩展后可进一步拆分：

- Memory：GPUVM vs fault/migration；Leader 保留 architecture/policy；
- Observability：software telemetry/trace vs PMU/profiling；
- Firmware：protocol/lifecycle vs HW-management services；
- RAS：evidence/health vs recovery/reset；
- Virtualization：只有产品需求与 HW 能力明确后再独立扩展。

## P. Leader Memory 深挖主题

继续建立 fault/replay ordering proof，至少同时跟踪四类 generation/sequence：

1. `mmu_notifier` sequence；
2. VM generation；
3. context generation；
4. reset generation。

测试矩阵应覆盖 HMM walk / migration / PTE publish / TLB invalidate / replay 与 `munmap()`、`mprotect()`、process exit、context destroy、GPU reset、FW restart 的交叉组合。
