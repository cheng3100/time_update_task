# 2026-08-08 Test Update #2

## Purpose
Second independent test run of the long-term GPU KMD owner-direction report. This run keeps the seven Stable Summaries unchanged and refreshes Living priorities plus owner-specific industry signals. Because this run happens only minutes after the previous test, it does not pretend that new patches appeared in the interval; instead it adds high-value signals that were not fully reflected in Test #1.

## A. Highest-value KMD feature priorities
1. **Memory** — Recoverable GPU page fault + HMM/SVM + migration + replay; next design target: migration granularity and compound/higher-order device pages.
2. **Firmware / Control Plane** — Versioned async KMD↔FW protocol + capability negotiation + restart generation/state reconciliation.
3. **Reliability / RAS** — Hang snapshot + devcoredump + persistent reset reason + heartbeat/watchdog; then fine-grained context/engine recovery.
4. **Multi-GPU / Fabric** — Stable device identity + topology + visibility/affinity + P2P capability model before peer/shared-VM work.
5. **Observability / Profiling** — eBPF KMD tracing + GPU object correlation; add PMU/per-process attribution when hardware counters are mature.

## B. Owner radar and latest industry signals

### 1. Memory / Virtual Memory / Unified Memory
**Current entry:** recoverable GPU fault → HMM → CPU/GPU migration → fault replay.

**New emphasis in this test:** migration granularity should be treated as an explicit second-stage architecture item rather than an implementation detail.

**Industry updates**
- **Linux DRM GPU SVM / drm_pagemap**: current documentation explicitly lists concurrent GPU faults, multi-GPU support, mixed system/device pages, compound device pages, higher-order DMA mapping for migration, common userptr and driver-side migration policy as future work.
  - Source: https://www.kernel.org/doc/html/latest/gpu/rfc/gpusvm.html
  - KMD impact: design fault/migration interfaces so 4K-only assumptions are not embedded into ownership/lifetime APIs.
  - Priority: **Now for architecture compatibility; 6–12 months for compound/higher-order migration experiments.**
- **Cross-vendor agreement on migration bottlenecks**: the same DRM SVM document records NVIDIA/AMD/Intel agreement that expensive core-MM calls in migrate-device paths are a performance bottleneck and compound device pages may reduce cost.
  - KMD impact: define migration-unit abstraction independently from CPU base-page size.
  - Priority: **6–12 months.**

### 2. Virtualization / Security
**Current entry:** SR-IOV PF/VF provisioning when ASIC supports it; otherwise VFIO/reset/ownership assessment.

**Industry updates**
- **Nova core abstraction**: nova-core is explicitly designed as a hardware/firmware abstraction base for upper drivers including nova-drm and a vGPU-manager VFIO driver.
  - Source: https://docs.kernel.org/gpu/nova/index.html
  - KMD impact: virtualization is increasingly coupled to a stable lower control-plane/resource model rather than duplicated per upper driver.
  - Priority: **6–12 months — reflect this in control-plane/resource-ownership interfaces.**
- **No high-value new GPU-specific SR-IOV kernel mechanism found in this short test window.** Linux PCI SR-IOV core remains mature baseline infrastructure rather than the differentiating KMD feature.
  - Source: https://origin.kernel.org/doc/html/latest/PCI/pci-iov-howto.html
  - Priority: **Do not create work merely around pci_enable_sriov(); wait for actual ASIC resource-partition requirements.**

### 3. Power / Performance
**Current entry:** busy/idle + utilization accounting → basic DVFS/runtime PM.

**Industry updates**
- **Firmware-managed PM remains the dominant architecture pattern** in modern GPU drivers: Intel Xe continues to separate utilization/frequency/runtime-PM mechanisms from firmware-managed control, while Nova documents firmware participation in GPU initialization and management.
  - Sources: Linux Xe firmware/PM documentation and Nova core documentation.
  - KMD impact: utilization accounting should be a stable KMD measurement layer, with policy/control protocol isolated behind FW capability APIs.
  - Priority: **Now.**
- **AMD uProf 5.3 (2026-06-17)** documents GPU profiling built on ROCm/rocprofiler hardware events and derived metrics.
  - Source: https://docs.amd.com/r/en-US/57368-uProf-user-guide/7.13.1.-GPU-Profiling
  - KMD impact: reinforces the need to make hardware utilization/performance counters consumable by profiling and PM policy as separate clients.
  - Priority: **6–12 months if PMU counters are available.**

### 4. Reliability / Recovery / RAS
**Current entry:** hang snapshot + devcoredump + reset reason + heartbeat/watchdog.

**Industry updates**
- **Xe devcoredump model remains the right crash-collection reference**: capture the relevant hang state before reset/recovery, then allow userspace to consume the preserved snapshot afterward.
  - Source: Linux Xe devcoredump documentation.
  - KMD impact: snapshot collection must be part of the failure path, not a debugfs read-after-reset mechanism.
  - Priority: **Now.**
- **Nova task list emphasizes GSP log-buffer export**, including retaining logs even when driver probe fails.
  - Source: https://docs.kernel.org/gpu/nova/core/todo.html
  - KMD impact: RAS snapshot format should include FW logs and early-boot/probe failure state, not only runtime rings/registers.
  - Priority: **Now / 6–12 months.**

### 5. Multi-GPU / P2P / Fabric
**Current entry:** enumeration + stable identity + topology + visibility/affinity + P2P capability matrix.

**Industry updates**
- **DRM GPU SVM lists multi-GPU support as active future work** and expects device-to-device memory interactions to coexist with common SVM abstractions.
  - Source: https://www.kernel.org/doc/html/latest/gpu/rfc/gpusvm.html
  - KMD impact: topology/P2P capability data should be first-class inputs to future shared-VM/migration policy.
  - Priority: **Now for device/topology model; shared VM later.**
- **fabric_ext (2026-07-28)** proposes eBPF policies spanning GPU, DPU/NIC and CXL fabric hooks using a semantic movement graph.
  - Source: https://arxiv.org/abs/2607.26335
  - KMD impact: not production-ready, but a useful signal that future fabric control may require explicit movement/ownership/ordering telemetry rather than only peer-copy APIs.
  - Priority: **Long-term watch; do not productize now.**
- **NCCLbpf (2026-03)** demonstrates verified programmable collective-communication policy in userspace NCCL plugins.
  - Source: https://arxiv.org/abs/2603.11438
  - KMD impact: collective-aware scheduling remains above KMD today, but KMD should expose topology/link/health primitives cleanly.
  - Priority: **Long-term watch.**

### 6. Observability / Profiling / Programmable Driver
**Current entry:** eBPF-based KMD dynamic tracing; PMU profiling second.

**Industry updates**
- **gpu_ext** continues to be the strongest research signal for a programmable GPU-driver policy layer using verified eBPF hooks across observability, scheduling and memory placement.
  - Source: https://arxiv.org/abs/2512.12615
  - KMD impact: near-term value is tracepoint/object-correlation discipline; policy hooks should remain research-only until safety/ABI requirements mature.
  - Priority: **Trace now; policy long-term.**
- **ProfInfer (2026-01)** shows non-intrusive eBPF profiling can correlate runtime functions, operator timelines and hardware-counter trends with low overhead.
  - Source: https://arxiv.org/abs/2601.20755
  - KMD impact: strengthens the case for a unified software-event + PMU timeline rather than separate debug and profiling stacks.
  - Priority: **6–12 months after the basic tracing framework.**
- **AMD uProf 5.3** shows production tooling consuming GPU hardware events through ROCm/rocprofiler.
  - KMD impact: PMU event naming/discovery/multiplexing and per-context attribution deserve explicit KMD interfaces.
  - Priority: **6–12 months if hardware allows.**

### 7. Firmware / Control Plane Architecture
**Current entry:** Versioned KMD-Firmware Async Control Protocol + Capability Negotiation.

**Industry updates**
- **Nova explicitly treats GSP firmware API instability as a core architectural problem**; nova-core aims to hide firmware-version-specific structure/semantic changes from upper drivers.
  - Source: https://docs.kernel.org/gpu/nova/core/todo.html
  - KMD impact: avoid scattered `if (fw_version >= X)` logic; capability and compatibility should be centralized in the control-plane layer.
  - Priority: **Now.**
- **nova-core is a lower-level reusable driver base for DRM and VFIO/vGPU upper layers.**
  - Source: https://docs.kernel.org/gpu/nova/index.html
  - KMD impact: reinforces separating HW/FW ownership and protocol from individual client/uAPI layers.
  - Priority: **Now for architecture; 6–12 months for state reconciliation/lifecycle expansion.**
- **GSP log export is listed as a concrete Nova task**, including failure-before-probe cases.
  - KMD impact: firmware health/debug channel should be part of the control-plane ABI from the beginning.
  - Priority: **6–12 months.**

## D. Deep-dive entry feature for this run: Migration Granularity
Once the basic recoverable-fault/HMM migration path works, define migration granularity as an architecture concept:

`fault range → residency decision → migration unit selection → DMA mapping unit → GPU PTE update unit → TLB invalidation unit → replay`

Do not assume all six units must remain 4K. The design should allow future 64K/2M/compound-device-page migration without rewriting page ownership/lifetime logic.

### 3–6 month deliverables
- record current page-size assumptions in fault/migration/PTE APIs;
- introduce an explicit migration-unit descriptor;
- measure cost breakdown for 4K migrations (MM calls, DMA mapping, copy, PTE/TLB work);
- prototype batched/higher-order mapping if HW/IOMMU permits;
- define fallback semantics for partial/mixed residency.

## E. Public future-evolution topic
Highest-value current signals:

3. Multi-GPU/fabric research is moving from raw P2P bandwidth toward programmable placement/movement/ordering policy.
4. eBPF is increasingly credible for observability and experimental policy, but production KMD policy hooks remain premature.
