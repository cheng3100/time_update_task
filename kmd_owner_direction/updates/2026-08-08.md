# 2026-08-08 Test Update

## Purpose
Initial snapshot for the long-term KMD owner-direction archive. This update validates the seven-owner taxonomy and records the current entry features. Stable summaries remain in `HOME.md` and `owners/*.md`.

## Current feature priorities
1. Memory: recoverable GPU fault + HMM + migration + replay.
2. Firmware: versioned async KMD↔FW protocol + capability negotiation.
3. Reliability: hang snapshot + devcoredump + reset reason + heartbeat/watchdog.
4. Multi-GPU: enumeration + topology + visibility/affinity + P2P capability matrix.
5. Observability: eBPF-based KMD dynamic tracing; PMU profiling is the second feature when hardware counters are ready.
6. Virtualization: SR-IOV PF/VF provisioning if ASIC capability exists; otherwise use VFIO/reset/ownership only as a preparatory project.
7. Power: busy/idle + utilization accounting, then basic DVFS/runtime PM when PM controls are reliable.

## Detailed entry feature: Firmware Control Plane

### Goal
Turn ad-hoc KMD↔firmware communication into a versioned control plane that can evolve without scattering firmware-version checks through KMD.

### First 3–6 month deliverables
- common message header and protocol version
- command/event namespace
- capability query/bitmap
- sequence ID and async completion
- standard timeout/error/unsupported-feature semantics
- firmware generation/restart detection
- re-handshake and capability refresh after restart
- first state-resynchronization rules

### Expansion path
Versioned ABI → async event framework → firmware lifecycle → state reconciliation → resource ownership → HW management offload → firmware-centric KMD architecture.

## Public future-evolution watch
- DRM GPU SVM / drm_pagemap and common migration abstractions
- DRM/Accel common infrastructure and compute uAPI evolution
- firmware-centric GPU drivers such as Nova-style hardware/firmware abstraction
- eBPF/gpu_ext-style programmable diagnostics/policy as a longer-term research signal

## Stability note
This dated file is allowed to change from run to run. It must not silently redefine the stable owner taxonomy; such taxonomy changes require an explicit decision and corresponding updates to `HOME.md` and owner summaries.
