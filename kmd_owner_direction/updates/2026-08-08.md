## D. Per-owner industry updates

### 1. Memory / Unified Memory
- **DRM GPU SVM / drm_pagemap:** common Linux design now explicitly covers shared CPU/GPU VM concepts, system↔device migration and device-private pages, with concurrent GPU faults, mixed pages, common userptr and migration policy as follow-on work.
  - Source: https://www.kernel.org/doc/html/latest/gpu/rfc/gpusvm.html
  - Impact: keep vendor HW fault/GPUVM mechanisms under a Linux-MM-facing abstraction; avoid locking UVM semantics into private APIs.
  - Priority: **Now**.
- **Compound device pages / higher-order DMA mapping:** NVIDIA/AMD/Intel agree migrate-device core-MM overhead is a bottleneck; compound pages and larger DMA mappings are named optimization paths.
  - Impact: after 4 KiB migration works, page granularity becomes an architecture feature.
  - Priority: **6–12 months**.

### 2. Virtualization / Security
- **Nova first-level core can serve DRM and VFIO/vGPU upper drivers.**
  - Source: https://docs.kernel.org/gpu/nova/index.html
  - Impact: build reusable resource/control abstractions instead of a virtualization-only hardware path.
  - Priority: **6–12 months architecture reference**.
- **No high-value new GPU-specific SR-IOV patchset found in this update window that changes the plan.** Linux PCI SR-IOV mechanics are already commodity; GPU-specific value remains resource provisioning, reset and isolation.
  - Source: https://origin.kernel.org/doc/html/latest/PCI/pci-iov-howto.html
  - Priority: **ASIC capability assessment first**.

### 3. Power / Performance
- **Xe runtime PM integrates PCI D3 state, VRAM constraints and outer lifetime references.**
  - Source: https://www.kernel.org/doc/html/latest/gpu/xe/xe_pm.html
  - Impact: PM design must coordinate MM/execution/dma-buf/PCI lifetime, not just program clocks.
  - Priority: **Now for architecture**.
- **GuC SLPC/PCODE demonstrate firmware-centric frequency policy.**
  - Sources: https://www.kernel.org/doc/html/next/gpu/xe/xe_firmware.html and https://www.kernel.org/doc/html/latest/gpu/xe/xe_gt_freq.html
  - Impact: keep measurement/policy/actuation boundaries explicit and define a clean FW PM service.
  - Priority: **6–12 months** if FW control is mature.

### 4. Reliability / Recovery / RAS
- **Xe devcoredump freezes crash state at hang time before recovery changes hardware state.**
  - Source: https://www.kernel.org/doc/html/latest/gpu/xe/xe_devcoredump.html
  - Impact: snapshot must be pre-reset and independent from later userspace readout.
  - Priority: **Now**.
- **Recovery should evolve by granularity rather than jump directly to full reset.**
  - Impact: define job abort → queue kill → context kill → engine reset → partial/full GPU reset, with state restore criteria.
  - Priority: **6–12 months after snapshot foundation**.

### 5. Multi-GPU / P2P / Fabric
- **DRM GPU SVM explicitly lists multi-GPU as future work.**
  - Source: https://www.kernel.org/doc/html/latest/gpu/rfc/gpusvm.html
  - Impact: establish device identity/topology/P2P capability independently so shared VM can consume it later.
  - Priority: **Now**.
- **GPU/CXL fabric policy research is becoming cross-layer.**
  - Source: fabric_ext, 2026-07-28: https://arxiv.org/abs/2607.26335
  - Impact: long-term Fabric owner likely includes movement observability/policy boundaries as well as P2P transport.
  - Priority: **Long-term watch**.

### 6. Observability / Profiling / Programmable Driver
- **Linux perf already supports complex system/fabric PMUs.**
  - Source: https://cdn.kernel.org/doc/html/latest/admin-guide/perf/nvidia-tegra241-pmu.html
  - Impact: GPU HW counters should evaluate perf/perf_event integration before inventing a fully private PMU interface.
  - Priority: **6–12 months when HW PMU is ready**.
- **gpu_ext explores verified eBPF policy hooks at GPU driver/device layer.**
  - Source: https://arxiv.org/abs/2512.12615
  - Impact: design stable events/object identities now; do not productize programmable policy yet.
  - Priority: **Now for tracing primitives; long-term for policy**.
- **fabric_ext extends programmable observability toward GPU/CXL movement paths.**
  - Source: https://arxiv.org/abs/2607.26335
  - Impact: unified KMD/FW/DMA/fabric timestamps and object correlation have long-term value.
  - Priority: **Long-term watch**.

### 7. Firmware / Control Plane
- **Nova makes the hardware/FW abstraction a first-level driver layer.**
  - Source: https://docs.kernel.org/gpu/nova/index.html
  - Impact: FW communication should become a formal architecture layer rather than feature-specific mailbox helpers.
  - Priority: **Now**.
- **Nova explicitly calls unstable GSP-RM firmware APIs an architectural problem.**
  - Source: https://docs.kernel.org/gpu/nova/core/todo.html
  - Impact: version/capability negotiation and version-specific translation belong below a stable KMD-facing API.
  - Priority: **Now**.
- **Intel GuC shows FW services expanding into PM policy.**
  - Source: https://www.kernel.org/doc/html/next/gpu/xe/xe_firmware.html
  - Impact: the control plane should support PM/reset/scheduler/telemetry service classes with shared async/error/version semantics.
  - Priority: **6–12 months after protocol foundation**.

## E. Detailed entry feature — Firmware / Control Plane

### Why now
Once a basic KMD/FW communication path exists, protocol debt grows quickly: feature-local command IDs, scattered FW-version checks, inconsistent timeout/error handling and restart behavior. The next useful step is not “more mailbox commands”; it is a formal control-plane contract.

### Proposed baseline message model
```c
struct fw_msg_header {
    u16 protocol_version;
    u16 msg_type;      /* request / response / event / error */
    u32 opcode;
    u32 sequence;
    u32 payload_len;
    u32 flags;
};
```

### 3–6 month deliverables
- protocol version and compatibility rules
- command/event namespace
- capability query/bitmap
- sequence ID and async completion
- standard timeout/error/unsupported semantics
- firmware generation/restart detection
- re-handshake and capability refresh
- first state-resynchronization rules

### Capability examples
- `CAP_GPU_FAULT_REPLAY`
- `CAP_DVFS`
- `CAP_PARTIAL_RESET`
- `CAP_MULTI_GPU`
- `CAP_SRIOV`
- `CAP_HW_SCHED`

Prefer capability checks over scattering firmware-version comparisons through KMD.

### Evolution path
Versioned ABI → async event framework → FW lifecycle → state reconciliation → resource ownership → HW management offload → firmware-centric KMD architecture.

### Boundary with Reliability
- Firmware owner: communication, FW lifecycle, restart protocol, re-handshake/state reconciliation mechanisms.
- Reliability owner: fault impact, containment, context/engine/GPU recovery strategy and user-workload restoration.
