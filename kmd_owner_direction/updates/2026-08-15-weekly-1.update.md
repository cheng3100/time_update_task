# 2026-08-15 GPU KMD Weekly Update — Curated

## Direction decisions
- Seven top-level Owners remain unchanged.
- Memory current entry remains recoverable fault + HMM + migration + replay.
- New emphasis: make a **fault/migration measurement contract** part of the first implementation so migration granularity can later be chosen from data rather than intuition.
- RAS remains snapshot-before-reset, with a new medium-term requirement for a stable management-facing GPU health/recovery-hint contract.
- Firmware Control Plane remains version/capability/async-first, with explicit boot/reset phase and generation state added to the near-term architecture.

## Highest-value industry signals this run

### Memory / Observability — Xe GT Statistics
Source: https://docs.kernel.org/next/gpu/xe/xe_gt_stats.html

Xe exposes low-overhead per-GT statistics including SVM fault count/time, TLB invalidation count/time, 4K/64K/2M fault and migration metrics, CPU/device copy time/bytes, get-pages time, bind time and reclaim-list counters. This is a strong reference for separating fault correctness from migration-granularity measurement and for combining always-on software telemetry with later trace/PMU attribution.

### RAS — Xe GPU Health Indicator / Device Wedging
Source: https://docs.kernel.org/next/gpu/xe/xe_device.html

Xe exposes `gpu_health` states and DRM wedged recovery hints. The reusable architectural lesson is a three-layer RAS model: raw evidence → KMD classification/recovery policy → management-facing health state/recovery hint.

### Firmware / Control Plane — Nova devinit
Source: https://docs.kernel.org/next/gpu/nova/core/devinit.html

Nova documents reset-time secure firmware/devinit sequencing, `GFW_BOOT`, and the relationship between low-level firmware initialization and suspend/resume. Self-developed control planes should model explicit boot/reset phases and generations, not only a boolean firmware-ready state.

### Virtualization / Power / Multi-GPU
No high-value direction-changing new item was found after the previous run. Keep ASIC-capability-first SR-IOV, measurement/lifetime-first PM, and topology-first Multi-GPU.

## Team feature split
1. Memory leader: recoverable fault/HMM/migration/replay + measurement/race matrix.
2. Firmware: versioned async protocol + capability + boot/reset generation/state reconciliation.
3. RAS: frozen snapshot/devcoredump/FW logs/reset reason + future health state contract.
4. Multi-GPU: identity/topology/visibility/P2P matrix.
5. Observability: stable object/event IDs + eBPF trace + low-overhead software counters.
6. Conditional: SR-IOV provisioning if ASIC supports it; otherwise Power telemetry/runtime-PM correctness.

## Deep-dive recommendation
Build a **Migration Granularity Measurement Matrix** for 4K, batched-4K, 64K and 2M covering HMM/get-pages cost, DMA mapping, copy setup/data time, GPU PTE update, TLB invalidation, internal fragmentation, false migration, CPU↔GPU bouncing and reclaim. The goal is to identify which granularity wins under which workload and hardware conditions, not to assume that larger pages are always better.
