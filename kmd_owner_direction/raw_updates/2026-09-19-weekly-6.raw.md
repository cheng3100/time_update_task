# GPU KMD Owner Direction 周度更新 — 2026-09-19

本期继续保持 **7 个一级 Owner taxonomy 不变**。本周没有出现需要新增第 8 个 Owner 的架构信号。相比上期把 VRAM reclaim/eviction 提升为 Memory P1，本期最值得吸收的不是一个全新的大方向，而是三个“正确性边界”信号：**fault-mode 必须是 VM 的显式 capability；reset 后 fence/ring/software shadow state 必须按 generation 重新对齐；FW shared-memory mapping 应由同时拥有 CPU/GPU mapping lifetime 的对象封装。**

本期核心判断：团队下一阶段不要继续增加零散 helper，而应把 **VM capability、reset reconciliation、FW shared-memory ownership** 做成跨 feature 可复用 contract。

## A. 本期最值得新增/增强的 5 个 feature

| 优先级 | Feature | Owner | 判断 |
|---|---|---|---|
| P0 | Recoverable Fault + HMM + Migration + Replay | Memory | 主线不变；新增“VM fault capability / scratch policy 必须显式建模” |
| P0/P1 | Reset Reconciliation Contract | RAS + Firmware | reset 后 ring/fence/doorbell/FW handle/software shadow state逐项重建或失效 |
| P1 | VF Resource Capability Matrix | Virtualization | SR-IOV VF 不能沿用 PF 初始化/恢复假设；每个 engine/ring 必须显式标注 present/initialized/restorable |
| P1 | VRAM Pressure + Reclaim/Eviction | Memory | 延续上期；机制与 policy 分层，不抢占 fault/HMM P0 |
| P1 | FW Shared-Memory Mapping Object | Firmware | CPU mapping + GPU mapping + bounds/VA translation + generation 由一个 owner 对象统一管理 |

## B. 七个 Owner + 子方向雷达

### 1. Memory / VM / UVM
GPUVM/page table → fault/replay → HMM/SVM → migration → reclaim/oversubscription → NUMA/large page → IOMMU/ATS/PRI/SVA → multi-GPU UVM/CXL。当前仍以 fault/HMM correctness 为 P0；reclaim 为下一阶段 P1。本周新增关注：VM 创建时必须显式区分 fault-mode 与 scratch/non-fault-mode，fault handler 不应仅凭“收到 fault”就假定 VM 可恢复。

### 2. Virtualization / Security
VFIO → PF/VF lifecycle → resource partition → PF-VF ABI → VF reset/FLR → migration → security/attestation。本周重点是 capability asymmetry：PF 与 VF、不同 VF 配置、不同 partition 下可存在不同 ring/engine/firmware resource，恢复代码不能假定“全功能对象都初始化过”。

### 3. Power / Performance
utilization → PM lifetime → runtime PM → DVFS/OPP → thermal/power cap → policy。本期没有足以改变路线的高价值新机制；继续 measurement/lifetime-first。

### 4. Reliability / Recovery / RAS
Detect → Freeze Evidence → Classify → Close Admission → Recovery Generation → Reset → Reconcile → Restore → Health。本周重点从“选择 reset scope”进一步进入 **reset reconciliation**：硬件 reset 完成不等于软件世界已恢复。

### 5. Multi-GPU / P2P / Fabric
identity → topology → visibility/affinity → directional P2P → peer mapping/P2P DMA → fabric health → shared VM/UVM。本期无方向级高价值新增；multi-XCC 修复提醒所有按 topology dimension 分配的数组/状态必须显式按实例数建模，但不把单 GPU XCC 错当成 multi-GPU feature。

### 6. Observability / Profiling
stable object/event/error ID → software counters → trace/eBPF → RAS events → PMU → unified timeline。本期没有比前期 DRM_RAS schema 更强的新接口变化；重点是让 reset reconciliation 事件进入同一 timeline。

### 7. Firmware / Control Plane
versioned ABI → parser/validator → async/seq → capability/property → generation/readiness → restart/reconciliation。本周 Tyr 的 MappedBo 设计强化了一个长期原则：共享 FW section 不应散落 CPU vmap、GPU VA 和 bounds check，而应由一个拥有双侧 mapping lifetime 的对象统一管理。

## C. 每个 Owner 当前切入点

Memory：recoverable fault + HMM + migration + replay；第一版补齐 VM fault-capability、mmu_notifier/process teardown/reset generation race。

Virtualization：先做 ASIC/SR-IOV capability assessment；若支持，PF/VF provisioning 之外同步建立 per-resource capability/presence/init/reset matrix。

Power：busy/idle/utilization + async-user quiesce，之后 runtime PM/DVFS。

RAS：Frozen snapshot + Recovery Admission/State/Sequence + Reset Reconciliation。

Multi-GPU：identity + topology + visibility/affinity + directional P2P matrix。

Observability：stable identity + software counter + eBPF，并加入 recovery phase/reconciliation result。

Firmware：Versioned Async Protocol + Capability Negotiation + Generation + shared-memory ownership + restart reconciliation。

## D. Industry Updates

### D1 Memory
**2026-09-17：Xe 修复 non-fault-mode scratch VM 接收 page fault 的问题。** 该修复要求来自不支持 fault mode 的 scratch VM 的 page fault 被拒绝，而不是进入普通 fault recovery。对自研 KMD 的价值是：`faultable` 应成为 VM/context capability，而不是 fault handler 的隐含假设。建议 VM 建立 `fault_mode / scratch_policy / replay_capability / PASID binding` 等显式属性，fault IRQ 首先做 capability validation，再进入 HMM/migration。优先级 P0 correctness。

**2026-09-16：AMDGPU GEM mapping-info ioctl 错误路径修复 object reference/exec lock 泄漏。** 这不是新架构，但对 Memory owner 很有工程价值：复杂 VM mapping introspection ioctl 一旦同时持有 GEM ref、drm_exec lock、动态 mapping array，所有失败路径都必须走统一 unwind。对自研 KMD 的 mapping query/debug uAPI，应优先采用单出口 cleanup/RAII 风格 ownership。优先级 P1 engineering correctness。

### D2 Virtualization / Security
**2026-09-16：AMDGPU SR-IOV VF UVD resume 修复。** VF 配置下 UVD decode ring 并未初始化，但 resume 路径过去无条件 force-complete fence，导致恢复路径访问未初始化 ring。核心启示不是 UVD 本身，而是 PF/VF capability asymmetry：`resource exists`、`resource initialized`、`resource owned by VF`、`resource participates in reset` 是四个不同状态。自研 PF/VF 第一版就应建立 resource capability matrix，并让 reset/reconcile 只遍历本 VF 实际拥有且初始化成功的对象。优先级 P1。

### D3 Power / Performance
**本期无高价值方向级新增。** 9 月 17 日公开的 AMD legacy PowerPlay voltage-index bounds fixes 说明 firmware/VBIOS 派生的 PM table 也必须做严格 validation，但它更属于输入验证/安全工程，不足以改变当前 utilization → runtime PM → DVFS 路线。当前仍应优先 PM lifetime、readiness、rollback，而不是新增 governor 项目。

### D4 Reliability / Recovery / RAS
**2026-09-16：AMDGPU KIQ reset fence reconciliation 修复。** KIQ ring 使用 polling fence 且 `noscheduler=true`，过去被通用 force-completion loop 跳过；MODE1 reset 后 writeback memory 中的硬件 fence 值可以存活，而软件 `sync_seq` 已继续前进，导致 reset 后第一次 KIQ submission 永久等待一个不会出现的序号。这个案例非常适合自研 KMD：reset 后必须逐类定义 `HW state survived? SW state survived? backing memory survived? sequence needs realign? pending completion stale?`。建议把它正式纳入 Reset Reconciliation Contract。优先级 P0/P1。

**2026-09-17：AMDGPU multi-XCC hung-queue array 初始化范围修复。** 原逻辑只按 MES pipe 数初始化，未乘 `num_xcc`，导致 XCC>=2 的状态未初始化。对 RAS 的价值是：hang/recovery bookkeeping 必须与真实硬件 topology cardinality 一致；不能让“控制结构数组维度”隐含绑定早期单实例假设。优先级 P1，尤其适合未来多 engine/XCC/partition 设计 review。

### D5 Multi-GPU / P2P / Fabric
**本期无高价值方向级新增。** multi-XCC 修复是 topology scaling 的好反例，但 XCC 仍是单设备内部 partition，不应为了周报把它包装成 Multi-GPU/Fabric 新方向。继续 topology-first、control/lifetime-second、data-path-third。

### D6 Observability / Profiling
**本期无高价值新增。** DRM_RAS Generic Netlink 的 node/error identity 仍是当前最值得跟踪的 common-layer 方向；本周更适合把新出现的 reset reconciliation 信息纳入现有 stable event schema，例如 `recovery_seq / reset_scope / object_id / pre_state / post_state / reconcile_result`，而不是再造一套 reset debug log。

### D7 Firmware / Control Plane
**2026-09-15：Tyr 引入 `MappedBo`，把 KernelBo 与 persistent CPU vmap 绑定到同一 lifetime。** Firmware section 在 load 时需要 CPU 写入，shared section 在整个驱动生命周期还要与 CSF interface 通信；`MappedBo` 让 CPU mapping 和 GPU mapping 由同一对象拥有，并为后续把 firmware-reported MCU VA 转换成经过 bounds validation 的 shared-section view 建立自然边界。对自研 R82/MHU/sharedmem 很有价值：共享区应由一个 service/object 同时管理 host VA、device/GPU VA、size/bounds、cache/coherency 属性和 FW generation。优先级 P1，建议进入 control-plane HLD。

## E. 长期 Learning Resources 本期新增/替换

本期建议只新增两条，避免把 resource 库变成新闻列表。

1. **Firmware / shared-memory transport：Tyr `MappedBo` patch series（Implementation / Practice）**。价值：它不是泛泛讲 shared memory，而是展示如何让 CPU mapping、GPU mapping 和 FW address validation 共享同一个 ownership lifetime。学习重点：persistent vmap lifetime、KernelBo ownership、FW-reported VA 到 validated view 的转换；注意 Tyr/CSF 的对象模型不能机械复制到 R82/MHU，但 ownership pattern 很值得保留。

2. **Virtualization/Security：AMDGPU Process Isolation 文档（Canonical / Implementation boundary）**。价值：展示 GPU 隔离不只是 IOMMU/VF，还包括跨进程 shader architectural state 的清理，以及 partition-aware isolation。学习重点：LDS/GPR cleaner、per-partition enable、job serialization；注意它不是 SR-IOV 隔离的替代品，而是 compute-state confidentiality 的补充层。

## F. 当前 5–6 人 feature project

建议保持六条线：Leader/Memory 继续 fault+HMM+migration+replay，并定义 fault-capability 与下一阶段 reclaim contract；RAS 负责 snapshot + recovery admission/generation + reset reconciliation；Firmware 负责 versioned protocol + shared-memory owner + generation/readiness；Multi-GPU 负责 identity/topology/P2P matrix；Observability 负责 stable ID/counter/eBPF + recovery timeline；第六人若 SR-IOV 硬件可用则做 PF/VF provisioning + capability matrix，否则继续 Power utilization/runtime PM。

## G. 本期重点 Feature：Reset Reconciliation Contract

### G1 为什么它比再写一个 reset helper 更重要
Reset 的真正问题不是“寄存器 reset bit 是否拉过”，而是 reset 前后的两个世界如何重新对齐。至少存在四类状态：硬件寄存器/engine state；device-visible memory 中的 ring/fence/doorbell state；KMD 软件 shadow state；FW 内部 resource/sequence state。不同 reset scope 对这四类状态的保留程度不同。

### G2 建议第一版建立 Reconcile Table
对每个资源记录：`owner`、`reset_scope`、`HW_survives`、`memory_survives`、`SW_shadow_action`、`FW_action`、`old_completion_policy`、`post_reset_validation`。

典型对象包括 command ring、completion ring、fence seq、doorbell、VMID/PASID、GPU page table root、TLB state、FW request seq、telemetry buffer、interrupt vector、queue/context handle。

### G3 reset 后统一阶段
建议流程固定为：`QUIESCE → SNAPSHOT → RESET → GENERATION_ADVANCE → RECONCILE_LOW_LEVEL → FW_REHANDSHAKE → RESTORE_GLOBAL → RESTORE/FAIL_CONTEXT → VALIDATE → REOPEN`。其中 `GENERATION_ADVANCE` 必须早于接收任何旧 async completion。

### G4 Fence/sequence invariant
KIQ 案例说明，reset 后 backing memory 可能保留旧 fence value，而软件 sequence 已变化。第一版必须回答：序号由谁 authoritative；reset 后是 force-complete、rebase、重新初始化还是全部 stale；polling fence 与 interrupt fence 是否不同；旧 completion 是否可能晚到。

### G5 3–6 个月路径
0–1 月：列全 reset-sensitive objects 和 reset scope matrix；1–2 月：实现 device-wide generation + stale completion rejection；2–3 月：ring/fence/FW request reconcile；3–4 月：VM/fault worker/context teardown race；4–6 月：fault injection 覆盖 reset during submit/fault/FW request/telemetry/context destroy，并输出 structured reconcile result。

### G6 1–2 年演进
从 device-wide reset 扩展到 engine/FW/context/queue/fabric-connection scope；每种 scope 有自己的 generation 和 restore capability。长期目标不是“更多 reset 类型”，而是形成可组合的 recovery state machine，让 Memory、Virt、Power、Observability 都只消费稳定 recovery contract。

## H. VFIO / SR-IOV
本期最值得加入的是 **VF Resource Capability Matrix**。每个 VF resource 至少区分 `present / initialized / assigned / active / resettable / migratable`。SR-IOV VF UVD 修复已经说明：仅靠 ASIC generation 或 PF 路径推断 VF 状态不可靠。未来 PF↔VF ABI、FLR、migration 都应消费同一 capability model。

## I. Power
路线不变。建议把 PM table / firmware-derived property validation 纳入 PM service ingress：范围检查、版本检查、dependency readiness、enable phase、rollback。不要因为本周 PowerPlay bounds CVE 就改变 Owner roadmap；它是“输入不可信”的实现纪律，不是新的长期方向。

## J. RAS
本期把 RAS 能力闭环正式扩为：`Detect → Freeze Evidence → Classify → Close Admission → Reset Scope → Generation Advance → Reconcile → Restore → Validate → Health State → Reopen`。其中 Reconcile 是本周新增最重要的一环。建议以后所有 reset code review 都必须附 reconcile table，而不是只看 reset register sequence。

## K. Multi-GPU
继续 identity/topology/P2P matrix。新增一个 review 纪律：任何 per-GPU/per-XCC/per-engine/per-port 数组必须显式写出 cardinality 来源和 hotplug/reset 生命周期，避免 multi-XCC 那类“按旧维度初始化、按新维度索引”的错误。这个纪律属于 Multi-GPU/Fabric 可扩展性，但本期不新增 feature。

## L. Observability
把 recovery/reconcile 纳入 stable event schema：`recovery_seq, scope, reason, object_type, object_id, old_generation, new_generation, reconcile_action, result, latency`。这样未来 eBPF/trace/devcoredump/management daemon 能回答“reset 为什么成功但第一条 submission 仍 hang”这类问题，而不依赖散乱 printk。

## M. Firmware
建议 shared-memory transport 引入统一对象，例如概念上的 `fw_shared_region`：同时拥有 CPU VA、device VA、size、alignment、coherency/cache attribute、access permissions、FW generation、bounds-checked offset/VA translation。上层禁止直接保存裸 MCU/FW address 并任意转换。Tyr `MappedBo` 是很好的 implementation pattern，但自研实现可更贴合 MHU/ringbuffer。

## N. Future Topic
本期重点跟踪四项：1) DRM/GEM `dma_resv` 正在讨论从 embedded object 转向 reference-counted dynamic reservation object，这可能改变 BO/reservation lifetime 边界；2) Rust GPU drivers（Tyr/Nova）继续形成 typed ownership、mapped object、FW address validation pattern；3) DRM_RAS common netlink 是否继续扩展 event/threshold/health；4) Linux MM/GPUVM 中 fault-mode、GUP/VMA semantics 是否继续显式化。它们目前都不构成第 8 Owner。

## O. 8–10 人拆分
Memory 可拆 GPUVM/TLB、Fault/HMM/Migration、Residency/Reclaim/QoS 三线；RAS 拆 Evidence/Health 与 Recovery/Reconcile；Firmware 拆 Protocol/Lifecycle 与 FW-managed services/shared-memory；Virtualization 在产品需求成立后拆 PF/VF provisioning 与 migration/security；Observability 拆 software trace/eBPF 与 PMU/telemetry；Multi-GPU 等真实 fabric silicon 后再拆 topology/control 与 data path。

## P. Leader Memory 深挖主题：VM Fault Capability × Reset Generation

本期建议把 fault handler 从“收到 fault → 查页 → replay”升级成 capability-driven state machine。第一步不是 HMM walk，而是验证：该 VM 是否 faultable；该 fault address 是否落在允许 fault 的 VA region；PASID/VMID/context generation 是否仍有效；当前 recovery generation 是否允许新 fault work；scratch/non-fault VM 是否应该直接 classify 为 fatal programming/error path。

建议明确四类 generation：`mmu_notifier_seq` 解决 CPU MM 变化；`vm_generation` 解决 GPU VM mapping/lifetime；`context_generation` 解决 queue/context teardown；`recovery_generation` 解决 GPU/FW reset world change。它们不能合并成一个全局 counter。

典型 race：fault IRQ 在 generation 10 到达，worker 排队期间 GPU reset 到 generation 11；即使地址和 PASID 看起来仍合法，旧 worker 也不能 publish PTE/replay。另一个 race 是 VM 从 fault-mode teardown 到 scratch/non-fault state，晚到 fault 必须被 capability validation 拦截。最终 replay 条件应是：MM state valid + VM/context generation valid + recovery generation unchanged + mapping/PTE/TLB completion valid + FW/GPU service ready。

这条主线与上期 reclaim/eviction 正好衔接：fault 是把 working set 拉近 GPU，reclaim 是把冷数据推远；两者必须共享 authoritative residency、generation 和 PTE/TLB ordering。Memory Owner 的长期价值就在于把这些并发状态统一成一个可证明正确的系统，而不是分别拥有几个 page-copy helper。

## 本期结论

七个 Owner 不变。本期最值得落地的两个动作是：**Memory 把 VM faultability/replay capability 变成显式对象属性；RAS/Firmware 联合建立 Reset Reconciliation Contract。** 这两项都直接服务当前已有 KMD 的“从能跑到可恢复、可扩展、可证明正确”。VRAM reclaim 继续作为 Memory P1，不抢占 fault/HMM correctness。
