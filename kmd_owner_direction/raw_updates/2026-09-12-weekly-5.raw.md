# GPU KMD Owner Direction 周度更新 — 2026-09-12

本期继续保持 **7 个一级 Owner taxonomy 不变**，没有新增第 8 个 Owner 的必要。当前最重要的变化不是扩大 Owner 数量，而是把现有 Owner 内部的 feature 从“功能点”继续推进成可测量、可恢复、可分层的系统能力。

本期两个最值得提升优先级的信号：

1. **Memory：device-memory cgroup + TTM reclaim/eviction 已经从 accounting 走向真正的显存压力控制。** Linux 的 dmem controller 已有 `dmem.max/min/low` 语义，TTM/Xe/AMDGPU 已有 reclaim 路径；最新 IGT v6 又补上同步 eviction、interruptible eviction 和 `O_NONBLOCK` 路径测试。这意味着 oversubscription / eviction / memory QoS 不再只是远期抽象，而可以开始定义独立的 KMD feature contract。citeturn565310search2turn565310search5turn565310search14
2. **Recovery / Virtualization / Observability：Intel Xe 面向 7.4 的首批 drm-xe-next pull 同时推进 VF multi-queue migration、parallel page fault、cold-reset recovery、DRM_RAS netlink/error threshold 与 structured SIGID logging。** 这些看似属于不同模块，实际上都指向同一个趋势：现代 GPU KMD 需要显式的 lifecycle、generation、error-state 和 userspace-visible contract。citeturn186079search1

Memory 的 P0 不变：

```text
Recoverable Fault
  → HMM / MMU invalidation correctness
  → Migration
  → GPU PTE publish
  → TLB completion
  → Generation revalidation
  → Replay
```

本期新增的是它后面的明确 P1：

```text
VRAM accounting
  → pressure detection
  → protected/unprotected residency
  → reclaim / eviction
  → oversubscription
  → memory QoS / tenant-aware policy
```

# C. 每个 Owner 当前切入点

**Memory**：继续 `recoverable fault + HMM + migration + replay`；并开始为下一阶段定义 `VRAM pressure / reclaim / eviction` 的对象模型、measurement 和测试契约。

**Virtualization**：ASIC capability gate 不变；如果 SR-IOV 可用，第一阶段不只做 provisioning，还要为未来 migration 明确 VF state serialization boundary。

**RAS**：Frozen snapshot + Recovery Admission/State/Sequence Contract，并新增 recovery scope/escalation：engine/FW/device/cold-reset。

**Multi-GPU**：stable identity + topology + port/peer + directional P2P matrix。

**Observability**：stable object/event/error identity + software counters + eBPF；RAS/PMU/FW log 共用 schema。

**Firmware**：versioned async protocol + capability/property + generation + service readiness + protocol-state truth-source discipline。

# D. 每个 Owner Industry Updates

## D1. Memory

### Update 1：dmem cgroup 的 eviction/reclaim 已进入可验证阶段

**时间窗口：2026-09-03 至本期。** Linux dmem controller 已定义 `dmem.max/min/low/current/capacity`，语义类似 memory cgroup，但对象是 device-memory region。TTM/Xe/AMDGPU 的 reclaim 路径此前已经形成；9 月初 IGT v6 进一步增加了 `write_eviction`、interruptible eviction，以及 `O_NONBLOCK` 降低 `dmem.max` 后由后续 BO allocation 触发 eviction 的验证。citeturn565310search2turn565310search5turn565310search14

这件事对自研 KMD 的价值不在“照搬 cgroup 文件接口”，而在于 upstream 已经把显存压力问题拆成几个清晰层次：

```text
Accounting
  ≠ Protection
  ≠ Reclaim mechanism
  ≠ Eviction selection
  ≠ Userspace QoS policy
```

自研 KMD 后续做 oversubscription 时也应该分层：

```text
VRAM usage accounting
     ↓
pressure watermark
     ↓
select evictable residency
     ↓
copy / unmap / PTE / TLB
     ↓
reclaim completion
     ↓
policy feedback
```

**影响：** 将 `VRAM Pressure + Reclaim/Eviction Contract` 提升为 Memory P1；但不替代 P0 fault/HMM。

**优先级：P1，建议在 fault/HMM 第一版稳定后立即立项。**

### Update 2：Xe CPU binds + ULLS migration queue 把 page-fault latency 当成独立性能目标

Xe 的 v6 系列展示了 fault/migration path 不仅要“正确”，还需要专门的 fast path。其测试数据显示，在 BMG 上持续处理 page fault 时，migration/copy job 使用 ULLS 相比传统 GuC submission 可快约 30–40μs，cold GPU 场景收益更大；系列还把 page-fault bind 从普通 migration exec queue 解耦，以避免 fence ordering 问题。citeturn186079search7

**影响：** 当前 recoverable fault feature 的 measurement contract 应从“fault 能否恢复”升级为：

```text
fault IRQ → resolve → migration/bind → PTE → TLB → replay
```

每一段都有 latency histogram，并区分 cold/warm、4K/large-page、copy/no-copy、contention。

**优先级：P0 measurement；专用低延迟提交机制 P1。**

## D2. Virtualization / Security

### Xe 面向 7.4 的 VF migration 开始覆盖 multi-queue

**时间窗口：2026-08-31 至本期持续进入 drm-next。** Xe 新一轮 pull 的重点之一是 **VF migration for multi-queue**。citeturn186079search1

现有 Xe VF migration 架构本来就需要保存/恢复 GGTT、MMIO、GuC firmware state、VRAM，并通过异步 migration data packet 与 VFIO read/write 接口传输；multi-queue 进一步意味着 queue 不再是孤立对象，而有 group/primary-secondary/firmware synchronization 关系。citeturn186079search14turn186079search6

对自研 GPU 的直接启示：

```text
VF migration state
  ├─ device identity / compatibility
  ├─ VM / page-table state
  ├─ queue-group topology
  ├─ doorbell / interrupt state
  ├─ FW scheduler/resource state
  ├─ VRAM / residency state
  └─ recovery generation
```

不能等做 live migration 时再发现这些对象根本无法序列化。

**影响：** 如果 ASIC 支持 SR-IOV，PF/VF 第一版的数据结构就应有 stable logical resource IDs 和 serialize/restore boundary，即使第一年不做 live migration。

**优先级：架构设计 P1；完整 live migration 仍是中后期。**

## D3. Power / Performance

### AMD UCLK DPM 修复再次证明 PM enable 顺序本身就是 ABI/lifecycle

**时间窗口：2026-09-09～09-10。** Apple Navi 14 某些板卡在 `EnableAllSmuFeatures` 时直接启用 UCLK DPM 会 timeout，导致 amdgpu 甚至无法形成 DRM device；修复把 UCLK DPM 从初始 feature enable 中移出，推迟到 post-init 单独开启，且作者明确指出“最早安全点”仍未知。citeturn268408search0

这与自研 GPU PM 的关系非常直接：

```text
power feature supported
        ≠
feature can be enabled now
```

需要至少区分：

```text
capability
readiness dependency
safe enable phase
failure rollback
post-enable validation
```

因此 Power Owner 的 FW PM protocol 不应只有 `SET_FREQ/GET_UTIL`，还需要明确 feature lifecycle。

**优先级：当前 PM/FW interface 设计中纳入；不改变“measurement → runtime PM → DVFS”主路线。**

## D4. Reliability / Recovery / RAS

### Update 1：Xe cold reset 把 recovery escalation 推到“设备完整断电再上电”

Xe 面向 7.4 的新功能引入 `DRM_WEDGE_RECOVERY_COLD_RESET`。其目标是处理一种普通 PCIe reset 或 driver reload 都无法清除的 persistent hardware error，由内核通过 uevent 告诉 userspace 需要完整 device power-cycle。citeturn226367search15turn186079search1

这说明 RAS 不应只有：

```text
reset = yes/no
```

而应形成 recovery hierarchy：

```text
Queue/Context kill
  ↓
Engine reset
  ↓
FW restart
  ↓
Device warm reset
  ↓
PCI reset
  ↓
Cold reset / power cycle
  ↓
Permanent failed
```

每一级都要定义：影响范围、是否保留 VRAM、哪些 handle stale、是否允许 replay、是否需要 userspace 协作。

**优先级：Recovery Contract 设计现在；cold-reset implementation 取决于平台硬件。**

### Update 2：7.3-rc1 AMD fault regression 展示“初始 fault 相同，但 recovery outcome 完全不同”

9 月 7 日公开的 gfx1150 regression 报告中，同类 gfxhub/SQC permission fault 在 7.2.3 可以被 containment：单 context/ring recovery 成功，应用 GPU process 重启，系统继续运行；而 7.3-rc1 路径出现 MES reset 失败并拖死 KFD queues。citeturn719387search12

**影响：** RAS 测试不能只测“能否触发 reset”，还必须有 recovery outcome matrix：

```text
fault scope
× reset scope
× affected queues
× unaffected queues
× FW state
× post-reset admission
```

并验证故障是否从一个 context 扩散到整个 device。

**优先级：当前 fault-injection / recovery validation P0。**

## D6. Observability / Profiling / Programmable Driver Infrastructure

### DRM_RAS netlink + error threshold + structured SIGID：错误观测正在形成正式 schema

Xe 面向 7.4 的 pull 包含 DRM_RAS netlink error event、error threshold 和 structured SIGID error logging。DRM_RAS 的 error notification 使用稳定 node-id/error-id 标识来源和错误类型；threshold 接口允许 userspace 查询/设置硬件在上报前的错误累计阈值。citeturn226367search1turn226367search9turn186079search1

这对自研 Observability 的价值非常大：

```text

```

不应是最终产品接口。应该建立：

```text
stable error_id
+ object identity
+ severity
+ source component
+ timestamp
+ generation
+ counter
+ threshold
+ recovery action/result
```

并让 devcoredump、tracepoint、eBPF、management daemon、未来 PMU timeline 共用这些 identity。

**优先级：Stable error/event identity P0/P1；netlink 或具体 userspace ABI 可后续选择。**

## D7. Firmware / Control Plane Architecture

### Xe mailbox PHASE 修复：protocol state 应尽量以真实硬件状态为 truth source

Xe system-controller mailbox 的 PHASE bit 每条消息都会 toggle。原实现软件缓存 `phase_bit`，错误路径会重置软件值；一旦软件缓存和硬件最后看到的 phase 漂移，之后所有消息都会带错 phase，firmware 会持续误读。修复方案不是增加更多软件修正，而是每次 frame 前直接读取硬件 `SYSCTRL_MB_CTRL` 中的 PHASE。citeturn398377search1

这对当前 R82/MHU/共享内存式 control plane 非常值得吸收：

> **凡是协议状态同时存在于 Host/KMD、FW 和硬件 mailbox/ring 中，要明确唯一 authoritative state；避免双方都维护可独立漂移的 shadow state。**

建议 protocol review 明确：

```text
producer index   authoritative owner?
consumer index   authoritative owner?
phase/epoch      hardware or memory?
seq              who allocates?
generation       who advances?
reset            who reinitializes which field?
```

**优先级：当前 Firmware protocol 第一版。**

## E1. Memory → Migration / Oversubscription：Linux cgroup v2 DMEM

**类型：Canonical / Spec。**

## E2. Memory → Migration / Oversubscription：IGT `cgroup_dmem` eviction tests

**类型：Implementation / Practice。**

**为什么值得长期留存：** 它把“显存 reclaim 应该如何验证”从抽象机制变成可执行 test design。

**学习重点：** pressure 构造、limit lowering、usage convergence、interruptibility、nonblocking semantics。

**注意：** IGT 场景基于 TTM/DRM；自研驱动应迁移测试思想，而不是机械复制接口。

# G. 本期重点切入 Feature：VRAM Pressure + Reclaim / Eviction Contract

这个 feature 很适合作为 Leader Memory 在 recoverable fault/HMM 之后的下一条 3–6 个月项目。

## G1. 为什么现在开始定义

基础 GPU KMD 的 memory 通常是：

```text
allocate BO
→ choose VRAM/GTT
→ bind
→ run
→ free
```

只要 VRAM 够大，这个模型可以长期工作。

一旦进入 AI / 多进程 / unified memory：

```text
working set > VRAM
```

就必须回答：

```text
谁应该留在 VRAM？
谁可以迁出？
迁到哪里？
什么时候触发？
谁承担 copy latency？
fault 和 eviction 是否互相打架？
reset 时正在 eviction 的 page 怎么办？
```

这就是独立 feature，而不是一个 `evict_bo()` helper。

## G2. 第一版对象模型

建议至少区分：

```text
Memory Object / Range
  ├─ logical ownership
  ├─ current residency
  ├─ preferred residency
  ├─ pinned / unevictable reason
  ├─ active / busy state
  ├─ reclaim priority
  ├─ last-access / hotness signal
  ├─ migration state
  └─ generation
```

不要直接把：

```text
BO in VRAM
```

等价于：

```text
BO must stay in VRAM
```

## G3. Mechanism 与 Policy 分层

### Mechanism

```text
select candidate
→ wait/sync active access
→ allocate destination
→ copy
→ publish new PTE/residency
→ TLB invalidate
→ release old backing
→ complete reclaim
```

### Policy

```text
谁先被选？
```

可以以后再演进：

```text
LRU
working-set
per-process priority
cgroup/tenant QoS
latency-sensitive protection
AI model weight protection
```

第一版绝不要把复杂 policy 写死在 migration mechanism 里。

## G4. 和 Recoverable Fault 的闭环

Fault 与 eviction 是一对反向动作：

```text
Fault:
System memory → VRAM

Eviction:
VRAM → System memory
```

因此它们必须共用：

```text
residency state
migration primitive
PTE update
TLB completion
VM/context/reset generations
measurement
```

否则以后会出现两套 page migration 代码。

## G5. 3–6 个月路径

### Month 0–1：Pressure / Measurement

先实现：

```text
VRAM total
VRAM used
VRAM reclaimable
VRAM pinned
per-process/context usage
migration bytes/time
reclaim attempts/success/fail
```

并定义 watermark：

```text
NORMAL
PRESSURE_LOW
PRESSURE_HIGH
CRITICAL
```

### Month 1–2：Manual reclaim primitive

先不做自动 policy，提供测试接口：

```text
reclaim N MB
```

验证完整 ordering。

### Month 2–4：Automatic eviction

加入简单 LRU / inactive candidate selection。

必须覆盖：

```text
evict vs submit
evict vs fault
evict vs context destroy
evict vs mmu_notifier
evict vs reset
evict vs dma-buf export
```

### Month 4–6：Protection / QoS prototype

加入类似：

```text
soft protected
hard unevictable
quota / max
low watermark protection
```

但仍然可以先用 debugfs/internal policy 验证，不急于冻结 uAPI。

## G6. 必测 invariants

```text
1. 已 publish 新 PTE 前不能释放旧 backing
2. TLB completion 前旧 translation 仍可能存在
3. active GPU access 不能被静默迁走
4. reset generation 变化后旧 migration completion 必须 stale
5. reclaim 失败不能留下 half-migrated residency
6. fault/reclaim 对同一 page 必须有串行化规则
```

## G7. 1–2 年演进

```text
Basic eviction
   ↓
Oversubscription
   ↓
Per-process / cgroup QoS
   ↓
Large-page-aware reclaim
   ↓
NUMA placement
   ↓
Multi-GPU residency
   ↓
Tiered / CXL memory policy
```

最终形成 Memory Owner 的第二个大闭环：

```text
Fault brings memory closer
Reclaim moves cold memory away
Policy controls who deserves scarce fast memory
```

# P. Leader Memory 本期深挖主题

本期建议重点研究：

# **Fault × Reclaim：同一页同时“想进 VRAM”和“想出 VRAM”时怎样保证 correctness**

这是从 recoverable fault 走向 oversubscription 最关键的桥。

## P1. Race 1：Fault 正在 migrate-in，pressure worker 同时选择它 eviction

```text
GPU fault page X
   ↓
System → VRAM copy in progress

同时

VRAM pressure
   ↓
select page X as eviction candidate
```

需要 invariant：

```text
MIGRATING_IN page cannot be selected for MIGRATING_OUT
```

但不能只靠一个 bool；必须和 range/page residency lock/state machine 对齐。

## P2. Race 2：Eviction 完成 copy-out，但 GPU PTE/TLB 尚未完成切换

```text
VRAM → System copy complete
        ↓
new PTE not fully visible
        ↓
old VRAM backing cannot free yet
```

正确完成条件应是：

```text
copy complete
AND new mapping published
AND required invalidate complete
AND generation still valid
```

之后才能 release old VRAM。

## P3. Race 3：Eviction 中 GPU reset

```text
migration generation = 20
recovery_generation = 8

copy...

GPU reset
recovery_generation = 9
```

旧 migration completion 必须 stale；恢复后根据 authoritative residency state 决定：

```text
rollback
or
rebuild mapping
or
refault
```

不能简单执行原 completion callback。

## P4. Race 4：CPU MM invalidation 与 eviction 同时发生

对于 HMM/userptr page：

```text
CPU munmap/mprotect
      ×
GPU eviction
```

要明确：

```text
mmu_notifier_seq
vm_generation
residency_generation
recovery_generation
```

分别解决什么问题，不能用一个全局 generation 代替全部。

## P5. 建议统一 Page/Range State Machine

长期可以形成：

```text
SYSTEM_RESIDENT
    ↓ fault/prefetch
MIGRATING_TO_GPU
    ↓
GPU_RESIDENT
    ↓ pressure
MIGRATING_TO_SYSTEM
    ↓
SYSTEM_RESIDENT
```

旁路状态：

```text
PINNED
INVALIDATING
STALE_BY_RESET
DESTROYING
```

真正的 Leader Memory 工作不是实现 `copy_page()`，而是证明：

> **fault、migration、eviction、MM invalidation、context teardown、GPU reset 组合出现时，任何 page/range 都只能处于一个可解释、可恢复的 authoritative residency 状态。**

这就是下一阶段从 HMM feature owner 走向完整 GPU Memory owner 的关键。

# 本期结论

本期七大 Owner 不变。最值得做的方向调整有两个：

1. **Memory：保持 recoverable fault/HMM P0 不动，但把 VRAM Pressure + Reclaim/Eviction 正式提升为下一阶段 P1 feature。** Linux dmem/TTM/IGT 已经提供足够成熟的机制和测试参考。
2. **RAS：从 Recovery Admission/State/Sequence 继续扩成 Recovery Scope + Escalation，明确 context/engine/FW/device/cold-reset 的层级。**

团队层面，当前 5–6 人无需改变七大 Owner 分法；下一步真正需要的是让每个 feature 都拥有明确的 object model、lifetime/generation、measurement 和 fault-injection contract，而不是增加更多模块名字。
