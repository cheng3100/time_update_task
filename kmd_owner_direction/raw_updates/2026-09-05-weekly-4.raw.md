# GPU KMD Owner Direction 周度更新 — 2026-09-05

本期继续保持 7 个一级 Owner taxonomy 不变，也没有新增第 8 个 Owner 的必要。相比上周 Fabric/remote invalidation 的强变化，本周更值得吸收的是“恢复、隔离和观测路径如何变成正式系统契约”：VFIO/PIC error recovery RFC 把 PCI AER recovery 从一个 eventfd 提醒推进到可查询的 recovery state + sequence + access guard；Intel Xe/Crescent Island PMT 则把 telemetry/crashlog access、共享 MMIO window、runtime PM、FW readiness 和 SR-IOV VF 边界放进同一访问协议。Memory 主线保持 recoverable fault/HMM/migration/replay，不因新项目新闻改变优先级。

## A. 本期最值得新增 / 增强的 Feature

| 优先级 | Feature | Owner | 本期判断 |
|---|---|---|---|
| P0 | Recoverable Fault + HMM + Migration + Replay | Memory | 主线不变；继续完成 invalidation/generation/measurement correctness |
| P0/P1 | Recovery State + Access Quiesce + Generation Contract | RAS | 本期重点增强；从 reset gate 扩成可复用 recovery contract |
| P1 | VFIO / SR-IOV Recovery State Propagation | Virtualization | ASIC/VFIO 条件满足后，错误恢复不应只发一个 event |
| P1 | Stable Object/Event ID + Telemetry Access Contract | Observability | 吸收 Xe PMT：telemetry 访问本身也有 PM/FW/locking 生命周期 |
| P1 | Versioned FW Protocol + Readiness / Service Lifetime | Firmware | 把 FW ready 从 bit 提升为可等待的 service readiness/lifecycle |
| P1 | Topology / Port / Peer + Directional P2P | Multi-GPU | 上周主线继续，无新的方向级变化 |
| P1/P2 | Utilization + Async-user Quiesce → Runtime PM/DVFS | Power | 强化 telemetry/crashlog/IRQ 等异步访问的 PM lifetime |

本期最重要的架构判断是：**Recovery 不应该只是 RAS 内部的 `reset()` 函数，而应形成一个跨模块可消费的状态/序列/访问准入契约。**

建议逐渐统一成：

```text
NORMAL
  ↓ error/hang
QUIESCING
  ↓
RECOVERY_IN_PROGRESS
  ↓
RESET_DONE / RESTORING
  ↓
NORMAL

fatal
  ↓
FAILED
```

并附带单调递增 `recovery_seq` / generation，使 Memory fault worker、FW async completion、VFIO/VMM、PM/telemetry access 都能判断自己看到的是不是旧世界的状态。

## B. 七个 Owner + 子方向雷达

### 1. Memory / Virtual Memory / Unified Memory

长期路线不变：GPUVM/page table/VMID/PASID/TLB → recoverable fault/replay → HMM/SVM/device-private → migration/oversubscription/eviction → large/compound pages → IOMMU/SVA → P2P/multi-GPU UVM → tiered/CXL memory。

当前优先级继续是：

```text
Fault/HMM correctness                 P0
MMU invalidation + teardown races     P0
Fault/migration measurement           P0
Migration granularity                 P1
Oversubscription/eviction             P1/P2
Remote mapping/invalidation           Architecture reserve
```

### 2. Virtualization / Security

保持 VFIO → SR-IOV PF/VF lifecycle → GPU resource partition → PF↔VF admin ABI → reset/accounting/isolation → vGPU/live migration → secure/confidential GPU。

本周新增的关键认识是：**assigned device 的 host recovery 也必须成为 guest/VMM 可理解的 control state，而不是一个无语义 eventfd。**

### 3. Power / Performance

保持 busy/idle → utilization → async-user quiesce → runtime PM → DVFS → thermal/power cap。本周 Xe PMT 再次说明 telemetry/crashlog/FW callbacks 也属于 PM lifetime 的 active users。

### 4. Reliability / Recovery / RAS

从现有：

```text
Detect → Freeze Evidence → Close Admission → Drain → Reset Generation → Recover → Restore
```

进一步增加：

```text
Publish Recovery State / Sequence
              ↓
Subsystems and userspace can retry / fail / wait safely
```

### 5. Multi-GPU / P2P / Fabric

继续 stable identity → topology → endpoint/port/peer → visibility/affinity → directional P2P → link state/counters → peer mapping/P2P DMA → remote control primitives → shared VM/multi-GPU UVM。

本周没有比上周 DRM Fabric + AMD UALink 更强的新方向级变化。

### 6. Observability / Profiling

继续三层：always-on software counters → trace/eBPF/object correlation → PMU/HW trace。本周补充一个重要维度：**telemetry transport/access path 自身也需要可观察和可恢复。**

### 7. Firmware / Control Plane

继续 raw FW ABI → parser/validator → version/capability translation → stable internal service → async request/completion → boot/reset generation → state reconciliation。本周强调 `FW_READY` 应当是 service readiness/lifecycle，而不是一个随处读取的 bool。

## C. 每个 Owner 当前切入点

Memory：继续完整跑通 `fault → PASID/VM/context → HMM → migration → GPU PTE → TLB invalidate → generation revalidate → replay`。

Virtualization：ASIC capability gate 仍然第一；同时在 VFIO/pass-through 研究中增加 recovery-state / access-blocking / retry semantics。

Power：建立完整 PM quiesce matrix，覆盖 IRQ、FW callback、fault/reset worker、telemetry/crashlog access。

RAS：Frozen snapshot + reset gate/generation，新增统一 `recovery_state + recovery_seq` contract。

Multi-GPU：继续 topology/port/peer/capability 模型，不提前实现 fabric data path。

Observability：Stable IDs + software counters + eBPF；telemetry/PMU access path必须明确 power/FW readiness/locking。

Firmware：Versioned async protocol + capability/property + parser/validation + boot/reset generation + service readiness。

## D. Industry Updates

### D1. Memory

本期没有发现足以改变当前 GPU SVM/HMM 路线的新 common-layer 机制。9 月 2 日 Tyr Rust GPU driver 新增 VM 和 BO ioctl 的 patch series 值得作为 Future Topic 观察：它将 userspace VM/BO interface 对齐 Panthor，并使用 per-file VM pool、xarray/ID abstractions 管理 VM。但这属于基础 GPUVM/uAPI 构建，不应该被包装成新的 Memory Owner feature。

来源：https://lwn.net/Articles/1091992/

对当前自研 KMD 的意义主要有两个：第一，per-file VM ownership/lifetime 仍然是现代 DRM driver 的基础抽象；第二，Rust driver 正在逐步覆盖真实 VM/BO uAPI，而不是只停在 probe/MMIO。但当前 Memory owner 仍应把资源投入 recoverable fault/HMM/migration correctness，而不是因为 Tyr 新增 VM ioctl 就改变路线。

优先级：**当前 feature 不变；Future Topic 跟踪 Rust DRM common abstraction。**

### D2. Virtualization / Security

9 月 1 日 VFIO/PIC error recovery RFC 是本周 Virtualization 最值得吸收的变化。当前 vfio-pci 遇到 PCI error 时基本只发一个 error eventfd，userspace 无法判断是可恢复 non-fatal error、需要 reset 的 frozen channel，还是永久失败，也不知道 host recovery 什么时候结束。因此 QEMU 往往只能把 VM 停在 internal error。

新 RFC 的核心不是“多几个 callback”，而是完整 recovery contract：

```text
error_detected()
  → record PCI channel state
  → block new device access
  → revoke BAR mappings / exported DMA-BUFs
  → quiesce interrupt
  → publish recovery state

host AER recovery / reset

slot_reset()
  → restore config state

resume()
  → restore access
  → wake waiters
  → publish completion
```

uAPI 引入 `VFIO_DEVICE_FEATURE_PCI_ERROR_RECOVERY`，包含 eventfd、status bits 和 sequence number；status 能表达 `IN_PROGRESS`、`CHANNEL_FROZEN`、`DEVICE_RESET`、`FAILED` 等，sequence 用来区分合并/快速完成的 recovery 事件。

来源：https://lwn.net/Articles/1091953/

对 GPU KMD 的启示非常强：未来 VFIO/vGPU/SR-IOV 即使 host 成功恢复 GPU，guest/VMM 也必须知道“什么时候不能访问”“这次 recovery 是否 reset 了 device”“旧 BAR/dma-buf/queue handle 是否仍有效”。因此 Virtualization Owner 的 recovery contract 应与 RAS 的 reset generation 对齐，而不是另做一套布尔状态。

优先级：**VFIO architecture reference 现在；真正实现取决于产品虚拟化需求。**

### D3. Power / Performance

本期没有新的 GPU-specific DVFS/governor 机制值得改变路线。但 9 月 1 日 Intel Crescent Island PMT v4 很有 PM lifecycle 价值：PMT 的 crashlog/telemetry 访问依赖 GPU 当前是否上电，telemetry 只在 device powered 时可用；访问共享 MMIO window 还需要 driver callback 选择正确 index/window，并且 FW 在 device power 时加载，PMT 需要 late-binding 等待 FW readiness。

来源：https://lwn.net/Articles/1092225/

这进一步证明 PM active-user 集合不只是 job/ioctl：

```text
job / submission
IRQ
FW callback
fault/reset worker
telemetry reader
crashlog reader
hwmon / PMT
```

全部可能访问 power-gated register/window。第一版 runtime PM 必须明确每条路径谁持有 PM ref、谁负责 drain、谁允许 wake device。

优先级：**runtime PM 第一版就纳入 telemetry/crashlog；复杂 governor 后置。**

### D4. Reliability / Recovery / RAS

同一 VFIO PCI recovery RFC 对 RAS 的价值甚至更高，因为它给出了一个很成熟的 recovery-state pattern：发生错误时立即关闭所有 access path，并让正在进行的操作 drain；recovery lock 只能用于发布状态/阻止访问，不能跨 PCI reset 持有，以避免与 `pci_bus_sem` 反向锁序；不便加锁的路径宁可 fail-safe 拒绝访问，也不能冒险访问正在恢复的设备。

来源：https://lwn.net/Articles/1091953/

这和当前 RAS 的 reset gate/generation 可以直接融合：

```text
recovery_seq++
state = QUIESCING
close admission
revoke/disable direct access
wait active users
freeze evidence
reset
restore
state = NORMAL / FAILED
notify waiters/userspace
```

本周建议把“Reset Gate”进一步重命名/抽象为 **Recovery Admission Contract**。Reset 只是 recovery action 的一种；non-fatal AER、FW restart、engine reset、fabric connection reset 都可以复用同一 control model。

优先级：**现在进入 RAS 第一阶段设计。**

### D5. Multi-GPU / P2P / Fabric

本期没有新的 production-level fabric 机制超过上周 DRM Fabric RFC 与 AMD UALink 大型 series。继续维持 topology/port/peer + directional capability 的 Living Entry，不因为本周缺少新 patch 就回退为简单 P2P bool matrix。

本周只补充一个边界提醒：VFIO recovery RFC 中对 BAR mapping、DMA-BUF export 的 revoke/guard 说明，未来 peer/fabric mapping 同样需要与 local/device/fabric recovery state 联动。也就是说未来：

```text
peer_mapping_generation
```

必须能被 device/fabric recovery 失效，但这一点继续留在 architecture reserve，不提前实现。

优先级：**Topology/control model 现在；fabric data path 后续。**

### D6. Observability / Profiling

9 月 1 日 Intel Crescent Island PMT v4 是本周 Observability 最有价值的新信号。PMT 不是单纯“暴露几个 counter”：CRI 的 PMT MMIO mapping 由多个 feature 共享，需要 index register 选择正确 memory space，因此 PMT core 增加 driver-specific access callback；crashlog/telemetry 访问还必须处理 runtime PM、FW late binding、hotplug 和 SR-IOV VF 差异。

来源：https://lwn.net/Articles/1092225/

这给自研 GPU PMU/telemetry 一个很具体的设计原则：**不要让 userspace/debug module 直接持有裸 MMIO window。** 更合理的是：

```text
Telemetry Consumer
      ↓
Stable Telemetry Service
      ↓
PM / FW readiness / privilege check
      ↓
window/index arbitration
      ↓
HW/FW data
```

如果底层 counter/crashlog 依赖共享 indirect window、power state 或 firmware readiness，这些都应由一个唯一 service owner 处理。否则 hwmon、debugfs、profiler、RAS 很容易各自抢 window / PM ref。

优先级：**software telemetry service 现在可借鉴；真正 HW PMU 视硬件成熟度。**

### D7. Firmware / Control Plane

本期没有新的 GSP/Nova major firmware ABI 变化超过上周 r000 series，因此 raw-ABI translation/validation 主线不变。但 Crescent Island PMT v4 提供了一个很有价值的“FW readiness”现实案例：PMT discovery/control information 依赖 device power 后加载的 firmware，因此使用 late-binding API 等待 FW ready，而不是假设 probe 完成后所有 firmware-backed service 永远可用。

来源：https://lwn.net/Articles/1092225/

这说明自研控制面中的：

```c
bool fw_ready;
```

长期应拆成更清晰的 service readiness：

```text
FW_GENERATION_N
  ├─ CORE_READY
  ├─ PM_READY
  ├─ TELEMETRY_READY
  ├─ SCHED_READY
  └─ MEMORY_SERVICE_READY
```

不同 service 可以有依赖关系和 readiness completion；reset/FW restart 后 generation 变化，旧 service-ready 状态自动失效。

另外 9 月 1 日 Rust `io` register projection v4 同时修改 Tyr 和 nova-core，目标是让复杂寄存器 block 使用 typed projections，而不是大量 relative register arithmetic。来源：https://lwn.net/Articles/1091993/ 。它不改变 Firmware Owner 路线，但说明 modern GPU driver 正在把 low-level MMIO ownership/type safety 进一步结构化，值得作为 Future Topic 跟踪。

优先级：**service readiness / generation 现在；typed-register infrastructure 作为长期工程参考。**

## E. 长期 Learning Resources 本期增量

本期只新增两组真正值得长期留存的资料，不为了数量修改其他 resource 页。

### 1. Virtualization → VFIO Passthrough / Ownership / IOMMU Isolation

新增：**VFIO PCI Error Recovery RFC（2026-09-01）**

类型：Implementation / evolving uAPI design。

是什么：给 generic `vfio-pci` 增加完整 PCI AER error recovery participation 和 userspace-visible recovery-state contract 的 19-patch RFC。

价值点：它比普通 VFIO 文档更深入地展示“assigned device 在 host recovery 期间如何真正关闭所有 access path”，包括 BAR、config、interrupt、runtime PM、DMA-BUF、reset 等，并明确 userspace 只观察 recovery，而不是参与 host recovery。

学习重点：`error_detected/slot_reset/resume`、access guards、BAR fault retry、DMA-BUF revoke、status + sequence uAPI、locking 与 `pci_bus_sem` ordering、AER fault injection。

学习注意：这是 RFC，不是冻结 uAPI；长期价值在 recovery/access-guard/state-sequence 模型，而不是记具体 bit 定义。

原始链接：https://lwn.net/Articles/1091953/

### 2. Observability → GPU PMU / Counter Discovery / Sampling / Multiplexing

新增：**Intel Crescent Island PMT support v4（2026-09-01）**

类型：Implementation / platform telemetry integration。

是什么：Xe driver 为 Crescent Island GPU 接入 Intel PMT，处理共享 MMIO access window、driver callback、crashlog/telemetry、runtime PM、FW late binding、hotplug 和 VF filtering。

价值点：它展示了真实 telemetry subsystem 的难点往往不在 counter 本身，而在 access ownership、power lifetime、firmware readiness、shared window arbitration 和 virtualization boundary。

学习重点：PMT callback access、shared indirect window/index、power sequencing、FW late binding、crashlog vs telemetry、SR-IOV VF handling。

学习注意：Intel PMT 是平台特定框架，不应照搬 API；应提取“单一 telemetry service owner + lifetime/arbitration”模式。

原始链接：https://lwn.net/Articles/1092225/

其余子方向本期没有高质量新增，保持 stable-growth 不动。

## G. 本期重点 Feature：Recovery Admission / State / Sequence Contract

### G1. 为什么值得现在做

你们后续几乎所有高级 KMD feature 都会碰到“设备正在恢复时怎么办”：

```text
submission
fault worker
FW async request
PM callback
telemetry read
VFIO BAR access
peer mapping
```

如果每个模块自己维护：

```c
bool resetting;
bool fw_dead;
bool device_bad;
```

很快就会形成互相不一致的状态机。

所以建议建立一个很小但统一的核心 contract：

```c
struct gpu_recovery_state {
        u64 seq;
        enum gpu_recovery_phase phase;
        enum gpu_recovery_scope scope;
        enum gpu_recovery_reason reason;
        enum gpu_health_state health;
};
```

概念上 `phase` 至少有：

```text
NORMAL
QUIESCING
RECOVERING
RESTORING
FAILED
```

`scope` 可以先只有 `DEVICE`，以后扩成 `ENGINE / FW / FABRIC_CONNECTION`。

### G2. Access Admission API

不同路径不应该直接判断 enum，而是走语义 API：

```text
gpu_access_begin(class)
  → OK
  → RETRY_LATER
  → FAILED

gpu_access_end()
```

不同 access class 可有不同策略：

```text
SUBMIT       → recovery 时拒绝
FAULT_WORK   → 检查 seq，允许 abort/retry
FW_MESSAGE   → old generation completion 直接丢弃
TELEMETRY    → 可等待/唤醒或返回 unavailable
CRASH_DUMP   → recovery 中反而允许特权读取 frozen state
```

### G3. Sequence / Generation

每次新的 recovery episode：

```text
recovery_seq = N
   ↓
error
recovery_seq = N + 1
```

所有长生命周期异步对象记录创建时的 seq/generation：

```text
fault_work.recovery_seq
fw_request.fw_generation
peer_handle.connection_generation
```

完成时必须 revalidate。

VFIO RFC 的 sequence number 很值得借鉴：即使 recovery 完成得比 userspace 处理 eventfd 更快，userspace仍能通过 sequence + status 判断自己错过了什么状态，而不是依赖“必须在 IN_PROGRESS 时刻读到它”。

### G4. Quiesce / Drain

进入 `QUIESCING` 后，明确关闭新 admission，并 drain 已经进入关键区的 operation。

至少建立矩阵：

| Access | 新请求 | 已在执行 | Recovery 后 |
|---|---|---|---|
| submit | reject/retry | wait or abort | re-submit policy |
| MM fault | reject/abort by seq | finish only if generation valid | refault |
| FW request | stop new | timeout/cancel | re-handshake |
| telemetry | wait/unavailable | finish with PM lifetime | retry |
| BAR/dma-buf | revoke/guard | drain refs | remap/re-export |

### G5. Locking 原则

VFIO RFC 给出的原则非常值得直接吸收：**recovery state lock 可以用于发布状态和 drain，但不要跨底层 reset 持有。**

否则 reset path 可能进入 PCI/PM/FW 等其他全局锁，形成 lock inversion。

更稳妥的结构：

```text
lock
  publish QUIESCING
  close admission
unlock

drain users
freeze snapshot

perform reset without recovery state lock

restore

lock
  publish NORMAL / FAILED
  wake waiters
unlock
```

### G6. 3–6 个月 Deliverable

第一版只处理 device-wide recovery：

```text
hang / fatal FW error
 → snapshot
 → close admission
 → drain
 → seq++
 → full device reset
 → FW re-handshake
 → restore minimal global state
 → contexts fail or explicitly recreate
 → reopen
```

同时至少有 fault injection：

```text
reset during submit
reset during HMM fault
reset during FW request
reset during telemetry read
multiple concurrent reset requests
recovery failure
```

### G7. 1–2 年演进

再扩展：

```text
DEVICE recovery
   ↓
ENGINE recovery
   ↓
CONTEXT / QUEUE recovery
```

以及：

```text
FW_GENERATION
FABRIC_CONNECTION_GENERATION
REMOTE_MAPPING_GENERATION
```

不同 scope 之间建立依赖图，而不是一个全局 `gpu_reset_counter`。

## H. VFIO / SR-IOV

当前总体判断仍是 hardware-gated。但 VFIO recovery RFC 让“虚拟化 feature 完整闭环”多出一个非常明确的组成部分：

```text
Provision
  ↓
Run
  ↓
Error
  ↓
Host Recovery State Visible to VMM
  ↓
Access blocked/revoked
  ↓
Reset/restore
  ↓
VMM decides resume/fail guest
```

因此未来 SR-IOV/vGPU owner 不只需要 PF↔VF admin protocol，还需要 **PF/VF/VMM recovery semantics**。如果 ASIC 支持 VF FLR/partition reset，更要定义 reset 作用域和旧 handle/queue/memory mapping 的失效规则。

## I. Power / Performance

本期继续坚持 measurement/lifetime first。

建议 PM quiesce matrix 新增明确的 telemetry/crashlog 行：

```text
telemetry read
crashlog read
hwmon
FW-backed PM service
```

对每项回答：

```text
需要 GPU 上电吗？
需要 FW service ready 吗？
能否触发 resume？
在 suspend/recovery 时是 wait、fail 还是读取 frozen cache？
```

这会避免未来 observability/debug path 反过来破坏 runtime PM correctness。

## J. Reliability / RAS

本期把 RAS 第一阶段正式概括为：

```text
Evidence Contract
      +
Recovery Admission Contract
      +
Recovery State/Sequence Contract
```

Evidence 负责“发生了什么”；Admission 负责“恢复期间谁还能进”；State/Sequence 负责“其他模块如何知道世界已经换代”。

这是比单独增加更多 reset 类型更重要的系统能力。

## K. Multi-GPU / P2P / Fabric

本周没有新的方向级变化，继续坚持：

```text
Topology first
Control/lifecycle second
Data path third
Shared memory policy last
```

但是 Recovery Contract 应预留 future `FABRIC_CONNECTION` scope，这样以后 peer connection reset 不需要重新发明一套独立 gate/sequence。

## L. Observability / PMU / eBPF

本期建议 Observability 增加一个内部概念：**Telemetry Service**。

它不是新 Owner，而是 PMU/Software counters 的 service boundary：

```text
Consumers
  ├─ debugfs/sysfs
  ├─ profiler
  ├─ RAS
  └─ power policy
        ↓
Telemetry Service
  ├─ access serialization
  ├─ PM lifetime
  ├─ FW readiness
  ├─ privilege/VF filtering
  ├─ counter discovery
  └─ snapshot/cache policy
        ↓
HW / FW counters / crashlog
```

这样 hwmon、RAS、profiler 不会分别直接控制共享 index/window。

## M. Firmware / Control Plane

当前 Firmware 第一阶段建议正式增加 **service readiness registry**：

```text
FW generation N
  ├─ CORE_READY
  ├─ MEMORY_READY
  ├─ PM_READY
  ├─ TELEMETRY_READY
  └─ SCHED_READY
```

每个 readiness 都属于 generation N。FW restart 到 generation N+1 后所有旧 readiness 自动失效，上层必须重新等待/negotiation。

这比一个全局 `fw_ready` 更适合长期演进，因为很多真实 firmware service 的启动顺序和恢复能力不同。

## N. Public Future Topic

本期最值得跟踪的 Future Topic 有四个：

1. Tyr Rust GPU driver 的 VM/BO uAPI 与 `drm-file` / Rust DRM common abstraction 演进：https://lwn.net/Articles/1091992/ 。它是 Rust GPU KMD 从基础框架走向真实 uAPI 的重要进展，但属于底座/公共机制，不是第 8 个 Owner。
2. Rust typed register projection v4 同时作用 Tyr 和 nova-core：https://lwn.net/Articles/1091993/ 。值得观察 Rust 是否形成更安全的 GPU MMIO/register block common patterns。
3. VFIO PCI error-recovery uAPI 是否收敛并获得 QEMU 正式消费：https://lwn.net/Articles/1091953/ 。如果收敛，会直接影响未来 accelerator passthrough 的 production recovery model。
4. Intel Xe PMT / platform telemetry 是否形成更通用 GPU telemetry integration pattern：https://lwn.net/Articles/1092225/ 。

这些均可自然归入现有 Owner 或 Future Topic，没有新增 Owner 的证据。

## O. 团队扩大到 8–10 人后的拆分

Memory：GPUVM/page-table 与 Fault/HMM/Migration 可拆 implementation sub-owner，Leader 继续持有 Memory architecture/policy。

RAS：如果 recovery feature 量明显增长，可拆 `Crash/RAS Evidence` 与 `Recovery/Reset` 两条 implementation line，但仍属于同一个 Reliability Owner。

Observability：可拆 Software Trace/Telemetry 与 PMU/Profiling。

Firmware：可拆 Protocol/Lifecycle 与 FW-managed HW Services。

Virtualization：只有真正存在 SR-IOV/vGPU 产品量后，再拆 Virtualization 与 Security。

Multi-GPU：真实 fabric silicon 到来后，可拆 Topology/Control 与 Fabric Transport；Memory policy 仍不并入。

## P. Leader Memory 本期深挖主题

本周建议做一个 **Fault Worker × Recovery Contract** 设计练习，把上一阶段的 MMU race matrix 与本周统一 recovery state 连接起来。

重点推演：

### Case 1：HMM walk 期间 recovery 开始

```text
fault worker: seq = 10
HMM walk...

RAS:
recovery_seq = 11
QUIESCING
```

HMM walk 即使最终成功，也不能直接 publish GPU PTE；必须在 publish 前 revalidate `recovery_seq / vm_generation / notifier_seq`。

### Case 2：migration copy 已完成，但 reset 即将发生

```text
CPU page → VRAM copy complete
GPU PTE 尚未 publish
```

如果 recovery 已开始，应该把这次 migration 视为 aborted/stale；不要为了“copy 已经完成”强行在旧 GPU generation publish PTE。

### Case 3：TLB invalidate request 在 reset 前发出

必须明确：

```text
TLB invalidate completion
```

是否还能在 reset 后到来？如果能，completion 也必须带 generation/seq，不能完成新世界的 request。

### Case 4：replay 之前 recovery state 改变

最终 replay condition 应变成：

```text
MM state valid
AND VM/context generation valid
AND recovery_seq unchanged
AND GPU/FW service ready
```

而不是仅仅：

```text
PTE installed == true
```

这个练习可以把 Memory 的 fault correctness 与 RAS/Firmware 的系统 lifecycle 真正接起来，是从单模块实现向系统级 owner 演进的关键一步。

## 本期归档结论

本期 Stable taxonomy 和 Stable Summary 均不修改。Living 层的核心变化是：RAS 从 reset gate 继续深化为通用 Recovery Admission/State/Sequence Contract；Virtualization 吸收 VFIO host-recovery state/uAPI 模型；Observability/Power/Firmware 从 Xe PMT 吸收 telemetry access、PM lifetime 和 FW service readiness 的完整生命周期。Memory 与 Multi-GPU 的当前优先级保持不变。
