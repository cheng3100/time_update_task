## D. Industry Updates by Owner

### 1. Memory / UVM
**GPU SVM N:1 per-device state is now an especially useful design reference.** Current next documentation describes one `drm_gpusvm_range` sharing a notifier while maintaining one `drm_gpusvm_pages` per `drm_device`; per-device DMA mapping state differs while logical range identity is shared.
- Impact: do not collapse CPU VA-range identity, device residency, DMA mapping and GPU PTE state into one object.
- Priority: architecture compatibility now; multi-GPU implementation later.

The same GPU SVM direction continues to keep mixed residency, migration, device-private memory, compound pages and higher-order DMA relevant to future Memory architecture.

### 2. Virtualization / Security
**VFIO CXL Type-2 passthrough v3 (2026-06-25)** adds a concrete future signal for CXL.mem-capable GPUs/accelerators: HDM decoder management, region exposure and component-register virtualization are required beyond ordinary vfio-pci passthrough.
- Impact: future accelerator passthrough may need memory/fabric ownership semantics beyond BAR/IRQ/IOMMU mapping.
- Priority: long-term watch unless current ASIC has CXL Type-2 ambitions.

Intel's current graphics virtualization support matrix continues to show SR-IOV as the production direction on multiple current graphics families.
- Impact: SR-IOV remains a real industry direction but still must be hardware-gated for a self-developed GPU.
- Priority: capability assessment first.

### 3. Power / Performance
No high-value direction-changing update appeared in this very short test interval.
- Keep measurement/lifetime constraints first.
- Telemetry should be reusable by DVFS and profiling rather than embedded inside one governor.
- Runtime-PM implementation should be validated as a lifetime/resource-ordering problem, not only a clock-control feature.

### 4. Reliability / RAS
**Production GPU crash tooling continues to become richer than register dumps.** AMD Radeon GPU Detective's hardware crash analysis and current Radeon Developer Tool Suite emphasize post-mortem correlation between crash state, in-flight work, execution markers and page-fault/resource information.
- Impact: a self-developed KMD crash artifact should evolve toward structured, versioned sections that offline tooling can consume.
- Priority: now for snapshot schema; richer workload correlation in 6–12 months.

Snapshot-before-reset remains the hard invariant; FW logs and early boot/probe failure evidence belong in the same diagnostic architecture.

### 5. Multi-GPU / P2P / Fabric
**fabric_ext (2026-07-28)** remains the newest high-value long-term fabric signal, treating GPU/DPU/CXL data movement as a semantic graph with source/destination, ordering, ownership and transformation metadata.
- Impact: future Fabric interfaces may need richer movement/ownership/link-health semantics than a boolean peer-copy capability.
- Priority: long-term watch; do not productize programmable fabric policy now.

For nearer-term engineering, topology-first remains the right sequence: identity → topology → P2P capability → peer mapping → P2P DMA → shared VM.

### 6. Observability / Profiling
**SysOM-AI (2026)** demonstrates continuous cross-layer diagnosis at production scale by combining CPU profiling, GPU kernel tracing and NCCL instrumentation using eBPF-based mechanisms, reporting <0.4% overhead across more than 80,000 GPUs.
- Impact: reinforces stable object IDs, timestamps and cross-layer correlation as more durable investments than one-off debug scripts.
- Priority: trace/object model now.

**Radeon GPU Profiler 2.7** remains a strong production example of combining event timeline with hardware-level performance information.
- Impact: PMU counter discovery should be designed to join the same workload/object timeline as software events.
- Priority: 6–12 months if HW PMU is mature.

### 7. Firmware / Control Plane
Nova guidelines continue to define a firmware-version-independent `nova-core` API as an explicit rule: second-level DRM/VFIO clients must not see version-specific GSP structures/semantics.
- Impact: centralize version translation and capability negotiation below a stable service API.
- Priority: now.

A July 31 draft NVK backend for `nova-drm` is an additional ecosystem signal that userspace is beginning to wire against Nova while the KMD/uAPI is still early. This is a direction signal, not evidence of a frozen production ABI.
- Impact: stable lower-layer contracts and explicit capability/versioning are more important while upper clients evolve.
- Priority: architecture now; track upstream rather than copy early API details.

## G. Detailed entry feature — Recoverable GPU Fault Service Contract

### Why this feature now
The first recoverable-fault implementation will define the lifetime model used later by HMM, migration, oversubscription, large pages and multi-GPU UVM. A path that merely “handles one page fault” without explicit concurrency/generation rules is likely to be rewritten later.

### Proposed state flow
```text
GPU access
  ↓
fault packet
  ↓
resolve device/PASID/VM/context
  ↓
validate fault generation + VM/context lifetime
  ↓
find process mm / VA range
  ↓
HMM / CPU PTE snapshot under notifier sequencing
  ↓
classify: invalid / already resident / map system page / migrate to VRAM
  ↓
DMA/residency resolution
  ↓
GPU PTE update
  ↓
TLB invalidate
  ↓
re-check generation / teardown state
  ↓
replay or terminate faulting workload
```

### Core correctness questions
1. What happens if `munmap()` invalidates the range while the fault worker is resolving it?
2. What if `mprotect()` or COW replaces a CPU PTE after HMM inspection but before GPU PTE publication?
3. What if process/context teardown races with migration completion?
4. What if GPU reset occurs while a replay token is pending?
5. How are duplicate/concurrent faults for the same page/range coalesced?
6. Which state is protected by `mmu_interval_notifier` sequence checking, and which requires KMD VM/context generation counters?

### Recommended state/generation objects
- `vm_generation`: invalidated on VM destruction/reinit.
- `context_generation`: invalidated on context teardown/reset re-create.
- `reset_generation`: increments for each GPU/FW recovery generation.
- per-range notifier sequence: tracks CPU-MM invalidation races.
- per-page/range migration state: idle / resolving / migrating / mapped / failed.

Do not assume one single generation counter can replace all of these; they protect different ownership domains.

### First 3–6 month deliverable
- one GPU / one process / one defined pageable-memory path;
- system→VRAM migration and migration-back on CPU access or explicit test path;
- recoverable vs fatal fault classification;
- GPU PTE + TLB + replay ordering documented as a state machine;
- tracepoints carrying PID/PASID/VM/context/fault IDs;
- tests for normal fault, duplicate fault, `munmap`, `mprotect`, COW/fork where applicable, process exit, OOM/migration failure and reset during fault;
- frozen fault diagnostic record for failures.

### 6–18 month expansion
- batched/concurrent faults;
- 64K/2M/compound/higher-order migration experiments;
- oversubscription and eviction loop;
- access/hotness metrics separated from migration mechanism;
- N:1 per-device metadata compatibility for future multi-GPU.

### 1–2 year owner closure
recoverable fault → HMM → migration → eviction/pressure → large-page/granularity → SVA/ATS/PRI → multi-GPU UVM → heterogeneous/tiered memory policy.

## H. VFIO / SR-IOV decision
The project remains hardware-gated. First validate SR-IOV capability, VF BAR/interrupt model, VMID/resource partition, reset/FLR semantics, IOMMU isolation and PF↔VF control path. CXL Type-2 VFIO work is a useful future signal but should not alter near-term scope unless the ASIC roadmap contains CXL.mem-capable accelerator behavior.

## I. Power / Performance
Keep reusable telemetry as the first durable layer. Measure busy/idle, engine utilization, frequency residency and memory bandwidth independently of the eventual governor. Runtime-PM correctness should be reviewed through active-reference ownership, resource ordering and suspend/resume state restoration.

## J. Reliability / RAS
The immediate design target is one structured crash object captured before destructive recovery. Recommended sections: reset generation, KMD version, FW version/generation/logs, queue/context/job IDs, VM/fault summary, ring/doorbell state, relevant registers, interrupt state, execution markers when available. Offline decoder/tooling should be a separate consumer.

## K. Multi-GPU
Remain topology-first. KMD owns stable identity, visibility, topology, peer capability and transport primitives. Collective algorithm policy remains in upper runtimes. Memory owner controls page residency/migration/shared-VM semantics.

## L. Observability / Profiling
The owner identity is not “eBPF”. Build one stable data model:
```text
device → client/PID/PASID → VM → context → queue → job
                                   ↘ fault/migration/FW seq/reset generation
```
Software events, FW events, PMU samples and crash snapshots should reuse these identifiers where practical.

## M. Firmware / Control Plane
Treat firmware-version independence as a design invariant. Upper services should consume stable commands/capabilities; FW-version translation stays below them. The control plane should later expose health/log service, restart generation and state reconciliation to RAS/Power/Virtualization clients.
