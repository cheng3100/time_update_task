# GPU KMD Owner Direction — 2026-08-29 Weekly #3

## Executive summary

七个一级 Owner taxonomy 保持不变。本期真正改变 Living priority 的最大信号来自 Multi-GPU/Fabric：AMD 在 2026-08-21 发布大规模 UALink Linux/AMDGPU patch series，已经具体进入 remote GPU memory、NPA address space、export/import authorization、remote TLB shootdown、remote interrupt 与 connection/reset handling；随后 2026-08-24 Intel/DRM 提出 vendor-neutral DRM Fabric RFC，以 `fabric → endpoint → port → peer` 建立协议无关的 accelerator topology object model。Multi-GPU 因此从“静态 identity/topology/P2P matrix”进一步明确为“identity/topology/link state/counters + transport/control primitives”，但 residency/migration/shared-VA policy 仍由 Memory Owner 负责。

Firmware 本期另一个高价值信号是 Nova r000 GSP firmware ABI v2：目标从适配具体 570.xxx firmware release 转向跨发布稳定的 r000 ABI，并把 MCTP/NVDM transport、msgq v2、GSP_INIT、bootloader/load-exec、state monitor 等一起作为一个版本化协议切换。Power 则出现 Imagination GPU runtime-PM race 修复：runtime suspend 前必须同步正在运行的 IRQ handler，说明 PM 的核心仍然是 active-user/quiesce/ordering correctness，而不是只做 clock gating。

## A. 本期最值得新增 / 增强的 Feature

1. **P0 Memory — Recoverable Fault + HMM + Migration + Replay + invalidation/generation contract**：路线不变，但开始为未来 remote peer invalidation 把“local TLB completion”和“remote mapping revocation”抽象分层。
2. **P0/P1 Multi-GPU — Topology/Link Model + P2P Matrix + Remote Control Primitive Contract**：在现有 identity/topology/P2P matrix 上增加 port/link state/counters、peer identity、remote invalidate/interrupt capability 的数据模型预留；当前不实现 UALink policy。
3. **P0 Firmware — Stable FW ABI Translation Layer + Versioned Transport/Lifecycle**：在现有 version/capability/generation 基础上，明确 raw FW ABI 与 stable KMD service API 之间的 translation layer。
4. **P0/P1 RAS — Frozen Snapshot + Reset Gate/Generation + Fabric/Peer Reset Semantics**：继续 reset gate，同时为未来 multi-device connection reset 明确 peer/fabric state 必须与 device reset generation 解耦。
5. **P1 Observability — Common Object Identity + Link/Remote-MM Event Schema**：继续 counters/trace/eBPF 主线，并预留 fabric endpoint/port/peer、remote invalidation、remote access retry 等 event identity。

Virtualization 继续 hardware-gated；Power 继续 utilization/runtime-PM correctness-first，没有新增第八个 Owner。

## B. 七个 Owner + 子方向雷达

### 1. Memory / Virtual Memory / Unified Memory
稳定主线仍为 GPUVM/page table/VMID/PASID/TLB → recoverable fault/replay → HMM/SVM/device-private → migration/oversubscription → large/compound page → IOMMU/SVA → dma-buf/P2P → multi-GPU UVM → tiered/CXL memory。

本期优先级：
- Recoverable fault correctness / measurement：P0
- Local TLB invalidation ordering：P0
- Migration granularity：P1
- Multi-GPU remote mapping/invalidation data model：P1/P2 架构预留
- Multi-GPU UVM policy：Later

### 2. Virtualization / Security
VFIO → SR-IOV lifecycle → GPU resource partition → PF↔VF ABI/reset/accounting → vGPU/live migration → secure boot/measurement/attestation。当前仍由 ASIC capability gate 决定是否立项 SR-IOV。

### 3. Power / Performance
Busy/idle → utilization → reusable telemetry → DVFS → runtime PM → thermal/power cap。新增强调 IRQ/workqueue/FW activity 与 suspend 的 quiesce ordering。

### 4. Reliability / Recovery / RAS
Heartbeat → frozen snapshot/devcoredump → classify/health → reset admission gate → reset generation → restore/replay → finer recovery。未来 fabric peer/connection reset 作为 device reset 的交叉问题，而不是直接塞进 device reset 一个 counter。

### 5. Multi-GPU / P2P / Fabric
Identity → topology graph → visibility/affinity → directional P2P matrix → peer mapping/P2P DMA → port/link state & counters → remote control primitives → shared VM → multi-GPU UVM/fabric health。UALink 和 DRM Fabric 使这一 Owner 本期从长期 radar 进入真实 upstream interface design 阶段。

### 6. Observability / Profiling
Always-on software counters → stable trace/object IDs → KMD/FW timeline → PMU/hardware trace → bottleneck attribution。对象模型未来增加 fabric/peer/link 与 remote-MM events，但不改变当前 entry feature。

### 7. Firmware / Control Plane
Versioned ABI → transport/msgq → async request/completion → capability/property object → boot/reset generation → stable FW translation layer → state reconciliation → resource ownership → FW-centric HW services。Nova r000 是本期最直接的现实参考。

## C. 每个 Owner 当前切入点

- **Memory**：GPU fault → PASID/VM/context lookup → HMM → migration → GPU PTE → TLB invalidate completion → generation revalidate → replay；继续测量每个 phase。
- **Virtualization**：先确认 SR-IOV/VF BAR/MSI-X/VMID/queue/doorbell/memory/engine partition、VF FLR、PF↔VF channel、IOMMU isolation。
- **Power**：可信 busy/idle + PM reference ownership + IRQ/FW/workqueue quiesce → runtime PM，再进入 DVFS。
- **RAS**：frozen snapshot + reset gate/generation；明确 peer/fabric connection state 不等价于 local GPU reset state。
- **Multi-GPU**：stable identity + topology + port/link state + directional P2P capability matrix；先构建 observation/control model，再做 shared VA。
- **Observability**：stable ID + software counters + trace/eBPF；新增 remote access/TLB/fabric event taxonomy 的预留。
- **Firmware**：versioned async protocol + capability/property + generation + FW ABI translation layer。

## D. Industry Updates

### D1. Memory

**2026-08-21 AMD UALink patch series 把 multi-GPU memory consistency 从抽象问题推进到实际 KMD implementation。**

UALink 方案允许 peer GPU 直接 load/store 远端 GPU memory，而不是做显式 copy；共享 memory 进入 NPA（Network Physical Address）空间，每个 GPU 维护独立 NPA page tables。更关键的是 exported memory 不永久 pin：exporter 可以因为 TTM eviction 或 MMU notifier 使 memory 移动/失效，因此必须向 importer 发 remote TLB shootdown，importer 侧还要用 presence check/retry 处理失效窗口。系列中已经出现 NPA VM、remote state、cross-GPU TLB shootdown、remote interrupt、export/import、revoke、connection reset、PTE mapping 等具体实现。

**对自研 KMD 的影响：** 当前 single-GPU fault/HMM 路线不应提前实现 remote UVM，但数据模型应继续坚持“logical object/range、local residency、local PTE、peer mapping、invalidation target”解耦。未来 multi-GPU memory consistency 很可能不是简单的 `for_each_gpu(tlb_flush)`，而是一个带 peer authorization、mapping lifetime、remote completion/retry、connection generation 的协议。

**优先级：** single-GPU correctness 现在；remote invalidation abstraction 只做架构预留；真实实现等 multi-GPU/fabric hardware。

### D2. Virtualization / Security

**本期无新的 GPU-specific SR-IOV / vGPU patchset 足以改变路线。**

因此继续坚持 ASIC capability first。值得注意的是 UALink exported-memory authorization 再次说明“能访问 peer memory”必须显式建立 authorization/ownership，而不能把可达性等价成权限；这与未来 multi-tenant GPU fabric/security 有交叉，但当前仍归 Multi-GPU + Security 的边界问题，不新增 feature。

### D3. Power / Performance

**Imagination GPU runtime-PM 修复提供了一个很具体的 PM correctness case。**

Linux 对 `drm/imagination` 的修复要求 runtime suspend 在真正关闭 GPU 前等待其他 CPU 上可能正在运行的 IRQ handler 完成；原实现可能出现 GPU 已 suspend，而 threaded IRQ 仍访问 GPU registers，最终触发 SError/panic。修复也去掉了在 IRQ handler 内临时 runtime-resume 的错误思路，避免 suspend/IRQ 的锁依赖死锁。

**对自研 KMD 的影响：** runtime PM 的 active set 不只是 job/IOCTL reference，还包括 IRQ handler、FW callback/workqueue、fault worker、reset worker 等异步执行上下文。设计 PM state machine 时要明确“谁可能访问 power-gated register/memory、如何 drain、谁负责 resume”。

**优先级：** PM feature 开始时就建立 quiesce matrix；复杂 governor 继续后置。

### D4. Reliability / Recovery / RAS

本期没有新的独立 reset framework 超过上周 Tyr reset gate 的价值，但 UALink implementation 把 **connection reset** 带进了 multi-device memory/transport lifecycle：export/import state、remote interrupt/TLB channel 和 peer connection 都需要 cleanup/recovery。

**对自研 KMD 的影响：** 将来 multi-GPU RAS 至少需要区分：
- local GPU reset generation；
- firmware generation；
- fabric/connection generation；
- peer memory export/import generation。

否则 local GPU 恢复后可能继续接受旧 peer channel、旧 remote completion 或旧 memory handle。

**优先级：** 当前只定义 generation ownership/boundary；等 fabric feature 真实立项再实现。

### D5. Multi-GPU / P2P / Fabric

这是本期变化最大的 Owner。

**第一，AMD UALink series 已进入生产 KMD 级别的对象和协议设计。** 2026-08-21 的系列约 95 个 patch，包含 UALink manager、pod/station configuration、NPA translation、remote state、remote TLB shootdown/interrupt、NPA dma-buf import control、opaque handle export/import、revoke、connection reset、remote PTE mapping 等。

**第二，2026-08-24 DRM Fabric RFC 提出 vendor-neutral、protocol-agnostic topology infrastructure。** 其 object model 是：

```text
fabric
  └─ endpoint
       └─ port
            └─ peer
```

其中 peer 是 typed identity/value descriptor，而不是必须指向 live kernel object；topology 表示 direct adjacency，不承诺 end-to-end reachability；port 可以包含 operational state/counters。这个边界非常适合长期 KMD：公共层负责 identity/topology/state，vendor driver 仍负责 firmware、memory semantics 和 data path。

**对自研 KMD 的影响：** 当前 Multi-GPU feature 应从单纯 `GPU0 can_peer_access GPU1 = true/false` 升级为：stable endpoint identity、directed port/link、peer identity、link state/counters、capability/reason code。未来上层 runtime、Memory UVM、RAS/Fabric health 都消费同一 topology object，而不是各维护一套设备矩阵。

**优先级：** 现在完善 topology data model；hardware 有 peer/fabric 后实现 provider；shared VM/UVM 和 fabric policy 后置。

### D6. Observability / Profiling

本期 Linux DAMON/perf RFC 提供了一个与 GPU observability 很相似的 pipeline-debug 模式：硬件 sampling backend 通过统一 observability API 暴露 per-CPU pipeline counters、debugfs statistics 和 tracepoints，用来定位“event 未创建 / 未 enable / HW 无 sample / ring drop / drain match 失败”等具体阶段，而不是靠 printk。

**对自研 KMD 的影响：** 当前 `software counters → trace/eBPF → PMU` 三层路线保持不变，但应再增加一个原则：复杂异步 pipeline 必须能对每个 stage 做 health/counter 观测。例如 future GPU PMU/fabric trace 可以分别统计 submission、HW production、ring overflow、consumer drain、decode/drop，而不是只暴露最终 sample count。

**优先级：** software pipeline counters 现在；HW PMU/AUX integration 后续。

### D7. Firmware / Control Plane

**Nova r000 GSP firmware ABI v2 是本期 Firmware 最重要变化。** 2026-08-21 v2 明确说明 Nova 当前运行 570.144 GSP firmware，而 r000 的目标是一个跨 release 稳定的 firmware ABI，因此 firmware filename 不再携带 release version。切换并不是只改一个 version number，而是同时改变 MCTP/NVDM headers、msgq v2 ring pointers/doorbell、load-and-execute event model、GSP_INIT handshake、ucodes/state-monitor buffers 等；patch series 还增加 transport validation 和 boot protocol checking。

**对自研 KMD 的影响：** “稳定 KMD↔FW ABI”不能理解为永远不改 wire format。更可靠的结构是：

```text
raw FW ABI vN
      ↓
transport/parser/validator
      ↓
translation + capability
      ↓
stable KMD service model
      ↓
Memory / Power / RAS / Virt
```

FW major-generation 切换时允许 wire protocol 成组演进，但 upper KMD service 尽量稳定；同时对 incoming length/version/vendor/sequence 做严格 validation。

**优先级：** 当前 versioned async protocol 就建立 translation/validation boundary。

## E. 长期 Learning Resources 本期增量

本期只新增三组真正值得长期保存的资料：

1. **Memory → Multi-GPU Unified Memory：AMD UALink infrastructure / documentation**
   - 类型：Implementation / Practice + upstream design。
   - 是什么：真实 AMDGPU 中 remote GPU direct memory access、NPA page table、export/import authorization、remote TLB shootdown/retry 的完整设计系列。
   - 价值点：它第一次把“multi-GPU shared memory consistency”从泛化概念落到 exporter/importer mapping lifetime 和 invalidation protocol。
   - 学习重点：NPA、export/import lifetime、TTM eviction/MMU notifier → remote shootdown、presence retry、remote PTE。
   - 学习注意：它是 UALink/AMDGPU 具体实现，不应照搬协议；抽取的是 ownership/invalidation/generation 模型。

2. **Multi-GPU → Shared VA / Fabric Health：DRM Fabric RFC + AMD UALink series**
   - 类型：Canonical/RFC + Implementation。
   - 是什么：DRM Fabric 提供 vendor-neutral topology object model；UALink 提供实际 data/control path case。
   - 价值点：两者恰好形成“common topology/control surface vs vendor memory/data path”的边界对照。
   - 学习重点：fabric/endpoint/port/peer identity、direct adjacency、port state/counters、provider ownership；以及 UALink remote interrupt/TLB/reset。
   - 学习注意：DRM Fabric 仍是 RFC；不要把当前 generic-netlink/uAPI 当冻结 ABI。

3. **Firmware → Boot/Restart Lifecycle：Nova r000 GSP ABI v2**
   - 类型：Implementation / evolving upstream architecture。
   - 是什么：Nova 从 release-specific r570 GSP 迁移到稳定 r000 ABI 的完整 patch series。
   - 价值点：非常适合学习一次真实 firmware major ABI transition 如何同时处理 transport、queue、boot handshake、validation、memory carveout 和 compatibility boundary。
   - 学习重点：MCTP/NVDM、msgq v2、GSP_INIT、load-exec、state monitor、transport validation。
   - 学习注意：对应 r000 firmware 尚未公开，系列明确要求 firmware 发布前不合入；学习架构，不依赖当前 patch API。

其余子方向本期没有高质量新增，不为了数量修改 resource library。

## G. 本期重点 Feature：Topology / Peer Capability Contract

### G1. 为什么现在做

以前 Multi-GPU 第一阶段可以只做：

```text
GPU list + BDF + P2P boolean matrix
```

本期 DRM Fabric/UALink 表明这会太快碰到边界：同一 GPU 可能有多个 physical ports；peer 可能是 GPU、switch、甚至由其他 OS 管理；direct adjacency 不代表 end-to-end reachability；capability 还会随 link/connection state 变化。

因此建议第一版 internal topology object 至少表达：

```text
gpu_device
  ├─ stable logical id
  ├─ physical/BDF identity
  └─ fabric endpoints[]
       └─ ports[]
            ├─ local port id
            ├─ peer type
            ├─ peer identity
            ├─ link state
            ├─ width/speed/capability
            ├─ health/error counters
            └─ generation
```

### G2. P2P capability 不再只返回 bool

建议内部接口概念上返回：

```text
reachable
transport type
read/write/atomic capability
peer memory mapping capability
remote invalidation capability
coherency attributes
reason if unavailable
connection generation
```

失败 reason 至少能区分 topology、ACS/IOMMU、aperture、peer offline、authorization、link health 等。

### G3. Boundary

Multi-GPU Owner 负责：
- 谁与谁相连；
- link/peer 是否健康、可达；
- transport/control primitive 是否存在；
- remote invalidation/interrupt 能力是否存在。

Memory Owner 负责：
- 一个 allocation 当前在哪里；
- 是否允许 export/import；
- page/residency/migration；
- shared VA / peer PTE lifetime；
- 何时需要 invalidation。

Firmware Owner 负责：
- fabric FW protocol / mailbox/ring；
- connection lifecycle；
- version/capability translation。

RAS 负责：
- peer/link failure 如何分类与恢复；
- reset/connection generation 如何使旧 state 失效。

### G4. 3–6 个月 Deliverable

即使没有真实 fabric hardware，也可以完成：
- stable GPU identity；
- PCIe/NUMA topology graph；
- directed P2P matrix + reason code；
- port/link/peer internal schema；
- synthetic topology test；
- tracepoint：peer add/remove、link state、capability change；
- UMD/debug tooling 能 dump 一个稳定 topology graph。

### G5. 1–2 年扩展

有 fabric hardware 后增加：
- provider/FW topology discovery；
- link counters/health；
- remote interrupt/invalidation primitive；
- peer memory mapping；
- connection reset；
- shared VM / multi-GPU UVM；
- topology-aware placement/replication policy。

最终形成真正独立的 Multi-GPU/Fabric owner，而不是“多卡枚举功能”。

## H. VFIO / SR-IOV

本期没有改变 hardware-gated 结论。完整项目仍应是：PF/VF resource model + versioned admin transport + provisioning + reset/FLR + accounting + isolation。不要把 generic PCI `sriov` enablement 当主体。未来如果 fabric/peer memory 进入虚拟化，还必须额外解决 tenant-visible topology、peer authorization、reset/connection isolation，但现在不提前产品化。

## I. Power / Performance

继续坚持 measurement/lifetime before policy。本期增加 PM quiesce checklist：submission/job、IRQ/threaded IRQ、FW callback、fault worker、reset worker、debugfs/sysfs/ioctl、dma-buf callback 中哪些路径会访问 power-gated register/memory；suspend 必须确保这些访问者已经 drain 或拥有 PM reference。第一版 runtime PM feature 应把这个矩阵写进设计文档和 fault-injection test。

## J. Reliability / RAS

当前 RAS 的主闭环仍然是 Detect → Freeze Evidence → Classify → Close Admission → Drain → Reset Generation Transition → Recover → Restore → Health State → Reopen Admission。

为 future multi-GPU 再增加一个规则：`device_reset_generation`、`fw_generation`、`fabric_connection_generation` 不应混为一个 counter。它们生命周期不同，只有明确的 dependency 才级联 invalidation。

## K. Multi-GPU / P2P / Fabric

本期正式把当前 feature 定义从“Enumeration + topology + P2P matrix”增强为：

**Enumeration + Stable Identity + Topology/Port/Peer Model + Visibility/Affinity + Directional P2P Capability Matrix。**

这不是改变 Stable Owner taxonomy，而是 Living entry feature 的深化。UALink data path、NPA、remote TLB、shared VM 仍属于后续阶段。

## L. Observability / PMU / eBPF

保持三层：software counters、trace/eBPF/object correlation、PMU/hardware trace。新增一个实践原则：异步 pipeline 必须每一级可观察，例如 PMU/fabric event 流至少要能区分 produce、enqueue、overflow/drop、drain、decode、consumer-drop。未来 fabric events 使用与 GPU job/fault 相同的 timestamp/generation 体系。

## M. Firmware / Control Plane

当前第一阶段应该明确包含四个边界：
1. raw transport/wire ABI；
2. parser/validation；
3. version/capability translation；
4. stable internal service API。

Nova r000 的现实案例说明 major protocol update 往往同时改变 transport header、queue semantics、boot event、init request 和 memory reservation；因此不要让 Memory/Power/RAS 直接依赖 raw FW struct。所有 async request/completion 继续携带 firmware/reset generation。

## N. Public Future Topic

本期最值得长期跟踪：
- DRM Fabric RFC 是否向 common DRM topology infrastructure 收敛；
- AMD UALink patch series 的 review 与 common DRM Fabric 的边界是否调整；
- UALink NPA/remote TLB 与 Linux GPU SVM/multi-GPU memory 的长期融合；
- Nova r000 firmware ABI 是否在 firmware 发布后进入合入阶段；
- DRM scheduler fair policy 在 7.2 revert 后如何重新推进；
- perf/DAMON hardware sampling observability 是否形成更通用 kernel-consumer pattern。

这些都不需要新增第八个 Owner。

## O. 团队扩大到 8–10 人后的拆分

- Memory：GPUVM/page-table 与 fault/HMM/migration 可以拆 implementation sub-owner，Leader 保留 overall memory architecture/policy。
- Multi-GPU：如果未来 fabric 硬件实际落地，可拆 topology/control 与 peer-memory/fabric transport implementation，但 shared residency policy 仍归 Memory。
- Observability：software trace/telemetry 与 PMU/profiling 可拆。
- Firmware：protocol/lifecycle 与 FW-managed HW services 可拆。
- Virtualization/Security：只有 SR-IOV/vGPU/confidential GPU 产品量足够时再拆。
- RAS 保持独立。

## P. Leader Memory 本期深挖主题

本周建议从上期的 fault/replay ordering proof 向未来多 GPU 延伸一步，但只做纸面模型：画出 **local invalidation → remote invalidation** 的 ownership/generation matrix。

至少区分：

```text
allocation_generation
local_vm_generation
mmu_notifier_seq
local_reset_generation
peer_connection_generation
remote_mapping_generation
```

再推演三个场景：
1. exporter 因 TTM eviction 迁移 allocation，而 importer 正在执行 remote load/store；
2. CPU `munmap/mprotect` 触发 notifier，同时 peer GPU 有 NPA/shared mapping；
3. peer connection reset 或 remote GPU reset 发生在 shootdown request/completion 中间。

要回答的不是“UALink 如何实现”，而是更基础的 owner 问题：**谁有权使 mapping 失效、谁等待谁的 completion、失败后是 retry/revoke/kill、哪个 generation 证明旧 mapping 已不可再使用。**

这个练习会把当前 single-GPU 的 MMU-notifier/PTE/TLB/replay correctness 自然延伸到未来 multi-GPU UVM，而不会提前把 Memory 路线绑死在某个 fabric 协议上。
