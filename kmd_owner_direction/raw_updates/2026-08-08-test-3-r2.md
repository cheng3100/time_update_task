## D. Industry Updates by Owner

### Memory
1. Linux GPU SVM / drm_pagemap remains the most important common-layer signal. The current documentation describes notifiers/ranges, HMM/DMA/migration integration, device-private memory and retry-based race handling. It also keeps mixed residency, multi-GPU, compound device pages, higher-order DMA and driver-side migration policy as explicit future work.
   - Impact: preserve clear separation between Linux-MM-facing SVM abstractions and hardware-specific GPUVM/fault mechanisms.
   - Priority: now.
2. The `next` GPU SVM documentation now describes the N:1 case where one range can maintain per-DRM-device `drm_gpusvm_pages`, mapped independently by each DRM device.
   - Impact: useful architectural clue for future multi-GPU/shared-VA metadata: do not assume one range has only one device view.
   - Priority: design compatibility now; implementation later.

### Virtualization / Security
1. Current Xe configfs documentation exposes an SR-IOV `max_vfs` configuration that must be set before device binding/probe and controls PF mode / managed VF count.
   - Impact: a concrete upstream example that GPU SR-IOV requires driver-lifecycle and resource-mode configuration beyond generic `pci_enable_sriov()`.
   - Priority: use as architecture reference if the ASIC supports SR-IOV.
2. Nova continues to place the HW/FW abstraction below both DRM and a possible VFIO/vGPU manager.
   - Impact: virtualization should consume common control/resource services rather than duplicate them.
   - Priority: 6–12 month architecture reference.

### Power / Performance
No new high-value direction-changing item appeared in this very short Test #2→#3 window.
- Existing strongest signal remains Xe runtime PM + firmware-mediated control: measurements/lifetimes/constraints in KMD, low-level actuation potentially in FW/HW.
- Priority: measurement/telemetry first; do not jump to a complex governor.

### Reliability / Recovery / RAS
No new direction-changing item appeared in this very short window.
- Xe devcoredump still strongly validates snapshot-before-reset.
- Nova's GSP log-buffer task reinforces preserving firmware evidence even when probe fails.
- Priority: frozen snapshot object + FW logs + reset reason now; recovery ladder after that.

### Multi-GPU / P2P / Fabric
1. GPU SVM `next` documentation's N:1 per-device page-state model is relevant to future multi-GPU/shared-VA design.
   - Impact: identity/topology and per-device memory view should remain separable from shared CPU VA.
   - Priority: topology-first now; shared VM later.
2. `fabric_ext` (2026-07-28) remains the newest strong research signal for GPU/DPU/CXL movement, ordering, ownership and observability policy.
   - Impact: long-term fabric interfaces may need richer semantics than peer-copy capability.
   - Priority: long-term watch, no productization now.

### Observability / Profiling
No new direction-changing item after Test #2.
- ProfInfer remains a strong example of joining eBPF runtime traces with hardware-counter trends.
- gpu_ext/fabric_ext remain research signals that justify stable object/event/timestamp hooks now, not programmable policy productization.
- Priority: trace/object correlation now; PMU integration 6–12 months if hardware exists.

### Firmware / Control Plane
1. Current Nova guidelines make firmware-version independence an explicit API rule: second-level drivers must not see FW-version-specific structures/semantics.
   - Impact: treat this as a design invariant for a self-developed KMD/FW control plane.
   - Priority: now.
2. Nova task list still calls out GSP-RM API instability and GSP log-buffer export, including probe-failure logs.
   - Impact: version translation + capability negotiation + FW health/logging should be formal services.
   - Priority: protocol now; health/log service next.
