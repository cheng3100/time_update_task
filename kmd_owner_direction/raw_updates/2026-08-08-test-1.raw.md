# GPU KMD Owner 路线测试更新 — 2026-08-08

下面按目前最终定义的 **7 个一级 Owner + 1 个公共未来演进 Topic** 做一次新的测试更新。由于不知道你们当前 ASIC 对 SR-IOV、PMU、preemption、P2P 等硬件能力的具体支持状态，涉及硬件前提的方向我会明确标记“满足条件再立项”，不会假定已经支持。

## A. 本期最值得关注的 5 个新 Feature

综合目前 Linux DRM/GPU 的演进，我会把当前优先级排成：

| 优先级 | Feature | 对应 Owner | 当前建议 |
|---|---|---|---|
| P0 | **Recoverable GPU Fault + HMM/SVM + Migration** | Memory | Leader 主线，立即持续推进 |
| P0 | **Versioned KMD↔FW Async Protocol + Capability Negotiation** | Firmware/Control Plane | 很适合成为新 owner 切入点 |
| P0/P1 | **Hang Snapshot + devcoredump + Reset Reason** | Reliability | 基本不依赖高级硬件，适合立即做 |
| P1 | **Multi-GPU Enumeration + Topology + Visibility + P2P Capability** | Multi-GPU | 很适合作为全新 feature |
| P1 | **eBPF KMD Trace + GPU Object Correlation** | Observability | 软件侧即可先行，适合立即试 |
| 条件 P1 | **SR-IOV PF/VF Resource Provisioning** | Virtualization | 必须先确认 ASIC SR-IOV capability |
| P1/P2 | **Utilization Accounting + DVFS** | Power | 取决于 PMU/firmware/clock control 成熟度 |

其中前三个我认为即便不掌握更多硬件信息，也可以直接进入设计阶段。

# B. 七个一级 Owner 当前状态

## 1. Memory / Virtual Memory / Unified Memory

**状态：最明确，继续保持。**

Linux DRM 的 GPU SVM RFC 现在已经把 `drm_pagemap`、device-private pages、system RAM ↔ device memory migration 等明确放入公共设计，而且未来计划已经包括：

- concurrent GPU faults；
- mixed system/device pages；
- multi-GPU；
- compound device pages；
- higher-order DMA mapping；
- common userptr；
- driver-side madvise / migration policy。

这说明你现在选的路线并不是某一家 vendor 的特殊实现，而正在逐渐成为 DRM/MM 层面的公共问题。

### 子方向雷达

```text
GPU Memory
│
├─ GPUVM
│  ├─ VA / PTE
│  ├─ VMID / PASID
│  ├─ TLB
│  └─ large/sparse page
│
├─ Recoverable Fault
│  ├─ fault classification
│  ├─ PASID → mm
│  ├─ PTE repair
│  └─ replay
│
├─ HMM / SVM
│  ├─ mmu_notifier
│  ├─ HMM mirror
│  ├─ device-private page
│  └─ shared VA
│
├─ Migration
│  ├─ CPU → VRAM
│  ├─ VRAM → CPU
│  ├─ eviction
│  └─ oversubscription
│
├─ IOMMU
│  ├─ ATS
│  ├─ PRI
│  ├─ PASID
│  └─ SVA
│
└─ Advanced
   ├─ NUMA
   ├─ compound pages
   ├─ multi-GPU UVM
   ├─ CXL/tiered memory
   └─ memory QoS
```

### 当前切入 Feature

> **Recoverable fault → HMM → migration → replay**

这里我暂时不改变。

### 下一阶段值得提前关注

**Compound device page / migration granularity。**

GPU SVM 文档明确指出 NVIDIA、AMD、Intel 都认为 migrate-device 中一些 core-MM 操作是性能瓶颈，并把 compound device page 和 2M higher-order DMA mapping 列为后续优化方向。

所以在你把基本 migration 路径做通以后：

> **4K migration → 64K/2M/compound migration**

很可能是一个自然的第二阶段。

# 2. Firmware / Control Plane Architecture

**状态：本期我认为应该显著提高优先级。**

Nova 是一个非常强的行业信号。

Linux Nova 现在明确把：

```text
nova-core
    ↓
hardware / firmware abstraction
    ↓
nova-drm
VFIO/vGPU manager
...
```

做成两层结构；`nova-core` 的目标之一甚至明确是提供 **firmware-version-independent API**，避免 GSP firmware 版本细节泄漏给二级 driver。

这与你们将来真正值得建立的 control plane 非常相似。

### 子方向

```text
KMD ↔ Firmware Control Plane
│
├─ ABI
│  ├─ protocol version
│  ├─ capability
│  ├─ command/event ID
│  └─ compatibility
│
├─ Async Protocol
│  ├─ sequence ID
│  ├─ async completion
│  ├─ timeout
│  ├─ cancellation
│  └─ error code
│
├─ Firmware Lifecycle
│  ├─ boot
│  ├─ handshake
│  ├─ restart
│  ├─ upgrade
│  └─ rollback
│
├─ State Model
│  ├─ KMD ownership
│  ├─ FW ownership
│  ├─ state sync
│  └─ state reconciliation
│
├─ FW-managed HW
│  ├─ init
│  ├─ engine management
│  ├─ PM
│  ├─ scheduler interface
│  └─ reset
│
└─ FW Health
   ├─ heartbeat
   ├─ watchdog
   ├─ crash dump
   └─ restart protocol
```

Nova 的 devinit 文档也很好地说明现代 GPU 中 firmware 已经参与 power sequencing、clock/PLL、thermal 等大量硬件初始化工作，而且部分流程在 suspend/resume 中仍然需要重新执行。

### 当前切入 Feature

> **Versioned KMD-Firmware Async Protocol + Capability Negotiation**

第一版建议真正做成：

```text
KMD                    FW
 │                      │
 │── HELLO(version) ───>│
 │<─ CAPABILITY SET ────│
 │                      │
 │── CMD seq=103 ──────>│
 │                      │
 │<─ ACK seq=103 ───────│
 │       ...
 │<─ COMPLETE 103 ──────│
```

必须具备：

- protocol version；
- capability bitmap；
- seq ID；
- async response；
- timeout；
- FW error；
- unsupported command；
- restart detection；
- re-handshake。

### 3–6 个月合理交付

不是“重写 firmware”。

而是：

> 把现有散乱 KMD/FW 通信提升为一套**有正式 ABI contract 的 control plane**。

### 1–2 年后

自然增长到：

> **Firmware-centric GPU control architecture**

我认为这完全足够形成长期 owner。

# 3. Reliability / Recovery / RAS

**状态：非常适合作为当前新 Owner。**

Intel Xe 已经使用 Linux `dev_coredump` 做标准化 GPU crash dump，并强调一个非常重要的设计原则：

> snapshot 必须在 hang 时获取，而不是用户读取时再获取，因为此时 GPU 可能已经 reset/recover。

这对你们自己设计 KMD crash infrastructure 很有参考价值。

### 子方向

```text
Reliability
│
├─ Health
│  ├─ heartbeat
│  ├─ watchdog
│  └─ progress tracking
│
├─ Detection
│  ├─ job hang
│  ├─ queue hang
│  ├─ engine hang
│  └─ firmware hang
│
├─ Snapshot
│  ├─ register
│  ├─ ring
│  ├─ queue/context
│  ├─ VM/PTE
│  └─ firmware
│
├─ Recovery
│  ├─ abort job
│  ├─ kill queue
│  ├─ kill context
│  ├─ engine reset
│  ├─ partial reset
│  └─ full reset
│
└─ RAS
   ├─ ECC CE/UE
   ├─ bad page
   ├─ page retirement
   ├─ AER
   └─ fault injection
```

AMDGPU 已经提供 block-level RAS、CE/UE injection、error count，以及 unrecoverable-error 策略，这很好地说明 RAS 最终绝不是 printk + reset。

### 当前切入 Feature

我仍推荐：

> **Hang Snapshot + devcoredump + persistent reset reason**

第一阶段：

```text
hang detected
     ↓
freeze diagnostic state
     ↓
register/ring/VM/FW snapshot
     ↓
devcoredump
     ↓
GPU reset
     ↓
userspace later reads original crash image
```

这是一个很标准、边界很清楚的新 KMD feature。

### 下一阶段

然后才做：

> **context/queue → engine → GPU 分级 recovery**

# 4. Multi-GPU / P2P / Fabric

**状态：非常适合成为“从零增加的新能力域”。**

而且这里和 Memory 的边界需要继续保持清楚：

- Multi-GPU owner 管 **device/topology/connectivity/peer mechanism**；
- Memory owner 管 **page residency/migration/Unified Memory policy**。

### 子方向

```text
Multi-GPU
│
├─ Device Model
│  ├─ physical GPU ID
│  ├─ logical GPU ID
│  └─ BDF/minor mapping
│
├─ Visibility
│  ├─ allowed GPU set
│  ├─ process/container visibility
│  └─ affinity
│
├─ Topology
│  ├─ PCIe root
│  ├─ switch
│  ├─ NUMA
│  └─ distance matrix
│
├─ P2P
│  ├─ capability query
│  ├─ peer BAR
│  ├─ peer mapping
│  └─ P2P DMA
│
├─ Shared VM
│  ├─ peer PTE
│  └─ common VA
│
└─ Fabric
   ├─ link management
   ├─ topology
   ├─ RAS
   └─ reset
```

GPU SVM 当前设计也已经把 **multi-GPU support** 明确列为后续工作，而且 `drm_pagemap` 的目标本身就考虑了未来 device-to-device fast interconnect。

### 当前切入 Feature

> **Multi-GPU Enumeration + Stable GPU Identity + Topology + Visibility/Affinity + P2P Capability Matrix**

例如最终形成：

```text
GPU0 0000:01:00.0 NUMA0
GPU1 0000:41:00.0 NUMA1
GPU2 0000:81:00.0 NUMA1

       GPU0 GPU1 GPU2
GPU0    -    NO   YES
GPU1   NO     -   YES
GPU2   YES   YES   -
```

### 第一阶段不建议做

不要一上来做：

> multi-GPU unified page migration。

那属于 Memory + Multi-GPU 两条线已经成熟后的交叉项目。

# 5. Observability / Profiling / Programmable Driver

把 PMU 合并进来以后，这个方向比之前明显完整了。

现在我认为应该有三个层次：

```text
Software Event
    +
Hardware Counter
    +
Cross-layer Correlation
```

## 软件侧

- eBPF；
- tracepoint；
- fentry/fexit；
- VM/fault/job/queue/FW event；
- PID/PASID/context/job correlation。

## Hardware PMU

- GPU cycle；
- CU/SM utilization；
- cache miss；
- memory bandwidth；
- stall；
- DMA/fabric counter；
- sampling；
- multiplexing。

Linux perf 对各种 system/uncore PMU 已经有成熟抽象。例如 NVIDIA Tegra 的 system PMU 已通过标准 PMU interface 暴露 SCF、NVLink-C2C、PCIe 等 bandwidth/latency/utilization 事件。

这对以后 GPU PMU 怎么接 Linux perf 是很好的模型。

## 长期目标

```text
UMD event
    │
KMD trace
    │
FW event
    │
GPU PMU samples
    │
    ▼
Unified Timeline
    │
    ▼
performance / fault attribution
```

### 当前切入 Feature

仍然建议先：

> **eBPF-based KMD Dynamic Trace**

原因是：

- 不依赖 GPU PMU 完成；
- 可直接服务当前 bring-up/debug；
- 后续自然接 PMU。

最低第一版：

```text
gpu-trace --pid
gpu-trace --pasid
gpu-trace --fault
gpu-trace --vm
gpu-trace --fw
gpu-trace --reset
```

### 第二切入 Feature

如果硬件 PMU 已经基本可用：

> **GPU PMU Counter Enumeration + per-process/context Attribution**

之后二者合并。

### 长期 programmable 方向

`gpu_ext` 已经明确提出 GPU driver/device 可成为 eBPF extensible policy interface，并探索 memory placement、scheduling 和 observability policy。现在仍是研究方向，但足以成为这个 owner 的 2–5 年技术雷达。

所以当前：

**eBPF trace：做。**

**GPU PMU：硬件成熟就做。**

**eBPF policy：观察，不产品化。**

# 6. Virtualization / Security

本期这里最重要的不是“去实现 VFIO”。

而是首先做一个明确的：

> **Hardware Virtualization Capability Assessment**

### SR-IOV

Linux PCI core 已经提供非常成熟的 SR-IOV PF/VF enable/disable model；VF 会作为独立 PCI function 出现，因此真正 GPU-specific 的价值在后面的 **resource virtualization**，而不是 `pci_enable_sriov()` 本身。

也就是说，如果 ASIC 有 SR-IOV：

真正的 KMD feature 应该是：

```text
VF creation
    ↓
VMID/resource allocation
    ↓
doorbell
queue
interrupt
VRAM/aperture
    ↓
PF ↔ VF ABI
    ↓
VF FLR/reset
```

### 当前判断

**如果硬件支持 SR-IOV：**

> 立即值得成为独立 owner 切入口。

Feature：

> **PF/VF Bring-up + VF Resource Provisioning/Isolation**

**如果硬件不支持 SR-IOV：**

VFIO passthrough 可以做，但我不会把“支持 VFIO”本身看成足够大的长期 owner 项目。

这时更合理是：

```text
VFIO passthrough
   ↓
GPU reset semantics
   ↓
IOMMU isolation
   ↓
device ownership
```

做 Virtualization owner 的预备项目。

### 中长期

Nova 的架构又给了一个很有意思的验证：`nova-core` 被设计为能同时服务 `nova-drm` 和 vGPU/VFIO manager。

所以：

> Control Plane 与 Virtualization 后面很可能会有非常强的架构交叉。

# 7. Power / Performance

这个方向保持成立，但优先级强依赖硬件。

Intel Xe PM 的设计很好地体现了一个合理演进：

- runtime PM；
- system suspend/resume；
- PCI D-states；
- RC6；
- GuC SLPC；
- frequency optimization。

所以不建议上来就做复杂 governor。

### 子方向

```text
GPU Power
│
├─ Utilization
│
├─ Idle Residency
│
├─ Runtime PM
│
├─ Clock Gating
│
├─ Power Gating
│
├─ DVFS
│
├─ Thermal
│
├─ Power Cap
│
└─ Workload-aware Policy
```

### 当前切入 Feature

> **GPU Busy/Idle Accounting + Utilization Sampling**

第一阶段只回答：

```text
GPU 什么时候 busy？
GPU busy 多少？
哪个 engine busy？
多久 idle？
```

然后：

```text
utilization
   ↓
basic DVFS
   ↓
runtime PM
```

这是最稳的切入顺序。

# C. 当前 5–6 人，我会怎么选项目

现在有 **7 个长期 owner**，但只有 5–6 人，因此我不会要求七条都立即配人。

如果今天开始第二阶段开发，我会优先：

| 人 | 第一阶段 Feature Project | 自然形成 Owner |
|---|---|---|
| **你** | Recoverable Fault + HMM + Migration | Memory/UVM |
| A | Versioned FW ABI + Async Protocol | Firmware/Control Plane |
| B | Hang Snapshot + devcoredump + Reset Reason | Reliability/RAS |
| C | Multi-GPU Enumeration + Topology + Visibility/P2P Matrix | Multi-GPU |
| D | eBPF KMD Dynamic Trace | Observability/Profiling |
| E | **SR-IOV 或 Power 二选一** | Virt/Security 或 Power/Perf |

这里最后一个人的选择非常简单：

### ASIC 有比较完整 SR-IOV 硬件

优先：

> **Virtualization**

### 没 SR-IOV，但 PMU/PMU firmware/clock control 已具备

优先：

> **Power / Performance**

剩下那个方向先由公共团队维护/预研，而不是硬安排一个 owner。

我认为这种安排比“7 个方向就必须现在找 7 个人”更符合你前面定下来的原则。

# D. 本期重点展开：Firmware Control Plane 切入路径

这次我会选新加入的 Firmware 方向作为详细切入点。

## 现在为什么值得做

因为基本 KMD 已经能通信以后，最容易积累技术债的就是：

```text
cmd A = 1
cmd B = 2

FW version 1这样
FW version 2又增加字段

timeout 各处自己处理
event 各自解析
```

系统规模一大，最后 KMD/FW 会非常难演进。

### 推荐抽象

```text
struct fw_msg_header {
    version;
    msg_type;
    opcode;
    sequence;
    length;
    flags;
};
```

然后明确：

```text
REQUEST
RESPONSE
ASYNC_EVENT
ERROR
```

### Capability

例如：

```text
CAP_GPU_FAULT_REPLAY
CAP_DVFS
CAP_PARTIAL_RESET
CAP_MULTI_GPU
CAP_SRIOV
CAP_HW_SCHED
```

KMD 不应该通过：

```text
if (fw_version >= 37)
```

到处判断。

而应该：

```text
if (fw_caps & CAP_GPU_FAULT_REPLAY)
```

Nova 的 nova-core 目标就是隔离 firmware-version-specific implementation，让上层 driver 看见稳定 API，这一点非常值得借鉴。

### 3–6 个月

完成：

1. versioned message header；
2. capability negotiation；
3. sync/async request；
4. sequence；
5. timeout；
6. standard error；
7. restart detection；
8. re-handshake。

### 第二阶段

加入：

```text
firmware restart
      ↓
KMD detects generation change
      ↓
re-handshake
      ↓
capability refresh
      ↓
resource state reconciliation
```

这时候它已经不再是 mailbox helper，而是真正的：

> **GPU Control Plane**

# E. 公共未来演进 Topic

本期这里我认为最重要的是 **GPU SVM 正在变成 DRM common infrastructure**。

这是比普通 `drm_exec`/scheduler enhancement 更值得你们关注的东西。

当前 DRM GPU SVM RFC 已经把：

```text
mm_struct
   │
GPU SVM
   │
drm_pagemap
   │
device-private pages
   │
system ↔ device migration
```

组织成公共设计，而且明确考虑未来：

- multi-GPU；
- compound pages；
- driver-side migration policy；
- common userptr。

### 对你们的意义

如果你们现在设计自研 UVM：

**不要把所有 HMM/SVM semantic 写死在 vendor-private API 内。**

至少架构上预留：

```text
vendor HW mechanism
        ↑
driver abstraction
        ↑
Linux HMM / future DRM SVM model
```

这样未来如果 DRM GPU SVM 真正成熟，迁移成本会低很多。

---

第二个公共趋势是 **Accel 与 DRM 继续共享基础设施**。

Linux accel 明确设计为 DRM 基础上的 compute accelerator subsystem，并且它从一开始就把：

- single/multi-user；
- MMU；
- SR-IOV；
- profiler/debugger；
- scale-up/out

列为典型 accelerator 能力。

这对于自研 AI/GPGPU 驱动很重要：

> 不应该只研究传统 graphics DRM driver；`drivers/accel` 也越来越值得持续跟踪。

---

第三个趋势是 **firmware-centric driver architecture**。

Nova：

```text
hardware/FW
   ↓
nova-core
   ↓
DRM / VFIO / other upper drivers
```

是一个很值得观察的新范式。

我把它归类为：

> **现在就值得在架构设计中参考，但不需要照搬。**

---

# F. 本期 Leader Memory 深挖主题

这一期我建议你研究：

> **`drm_pagemap` 为什么要存在，以及它试图解决传统 HMM/device_private 模型的哪些 GPU-specific 问题。**

重点不是读 API，而是理解：

```text
struct page
mm_struct
dev_pagemap
drm_pagemap
GPU SVM
GPU VRAM allocator
```

五者的 ownership/lifetime。

特别回答：

- VRAM page 如何进入 `mm_struct`；
- CPU fault 如何把 device page migrate 回 RAM；
- GPU fault 如何反方向 migration；
- device unbind 为什么需要把 page migrate 回 system；
- multi-GPU 下一个 page 属于哪个 device；
- 为什么 compound device page 会影响 migration 性能；
- GPU0/GPU1 对同一 CPU VA 的 residency view 不一致时怎么处理。

这比继续停留在 `hmm_range_fault()` API 层面更接近未来 Unified Memory owner 的核心。

---

## 本次测试后的整体判断

现在这套 **7+1** 结构我认为已经比较稳定：

```text
长期 Owner
├─ Memory / Unified Memory
├─ Virtualization / Security
├─ Power / Performance
├─ Reliability / Recovery / RAS
├─ Multi-GPU / P2P / Fabric
├─ Observability / Profiling / Programmable Driver
└─ Firmware / Control Plane

公共未来 Topic
└─ DRM / Accel / uAPI / upstream / kernel evolution
```

这一期我没有发现一个足够强的新领域需要加入第 8 个 owner。反而当前更重要的是开始验证这七条线的**实际第一阶段 feature 是否与现有 ASIC/KMD capability 匹配**，特别是 SR-IOV、PMU、P2P、firmware ownership 这四项硬件条件。
